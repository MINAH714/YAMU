# YAMU 앱 UI/UX 설계 근거

사용자 앱(`fe/android`, Kotlin · Jetpack Compose)을 왜 이렇게 설계했는지 결정마다 이유와 근거를 모은 문서다. 모의 POS 웹(`fe/pos`)은 6장에 짧게 둔다. 기준은 develop `efe90f56`(2026-11-16, 모션 -499~-511 머지 뒤)이고 지금 앱을 같은 날 에뮬레이터로 찍어 대조한 결과와 고칠 목록은 7장 · 8장에 있다. 스크린숏을 곁들인 요약은 팀 공유 페이지(https://claude.ai/artifact/GFqRSx3QfGRm26LNao5gNP)에 있다.

## 읽는 법

결정마다 근거의 종류를 붙였다. 기록이 없는 이유를 지어내지 않으려고 '추정'을 따로 둔다.

| 코드 | 코드 주석에 이유가 적혀 있다 |

- 파일:줄은 따로 적지 않으면 `fe/android/app/src/main/java/com/yamu/app/` 아래 경로다.
- '설계 문서 01'처럼 번호로 부르는 문서는 `fe/android/README.md`가 말하는 저장소 밖 설계 문서(발표 폴더 `app-dev/`)다. 회의록도 같은 폴더의 `meeting-notes/`에 있다.

### 1.2 하단 탭을 쓴 이유

| 이유 | 근거 |
|---|---|
| 기획안 7장의 권장 하단 메뉴가 탭 다섯 개였고 앱 화면 지도(IA)를 이걸 기준으로 그렸다 | 기록: 와이어프레임 `GUIDE.md:41`, `boards/00-IA.png` |
| 자주 오가는 최상위 목적지가 넷이고 서로 비슷하게 중요하다. Android 문서는 내비게이션 바를 "Three to five destinations of equal importance", 좁은 화면, 어느 화면에서나 같은 목적지일 때 쓰라고 한다 | 지침: [Android 내비게이션 바](https://developer.android.com/develop/ui/compose/components/navigation-bar) |
| 레퍼런스 10개 중 탭 구성이 가장 비슷한 앱으로 신한 SOL페이(홈 · 혜택 · 결제 · 금융 · 카드 5탭)를 골랐다. 카카오페이도 하단 '결제' 탭을 두 번 누르면 결제 준비가 끝난다 | 비교: Story 8.1.1 `레퍼런스 앱 10개 정리.md` |
| 화면 아래쪽은 한 손으로 쥐었을 때 엄지가 닿는 자리라 자주 누르는 것을 둔다 | 추정(일반 원칙, 팀 기록 없음) |

### 1.4 탭 순서

| 자리 | 이유 | 근거 |
|---|---|---|
| 홈이 맨 왼쪽 | 앱을 켜면 처음 보는 화면이고 다른 탭 첫 화면에서 뒤로 가면 홈으로 온다. Android는 고정 시작 화면을 두고 거기서 뒤로 가면 앱을 나가게 한다 | 지침: [Principles of navigation](https://developer.android.com/guide/navigation/principles) "Fixed start destination", 코드 `navigation/NavExtensions.kt:11-25` |
| 소비분석이 두 번째 | Jira -478은 "소비분석을 두 번째로 옮긴다"고만 적었다. 결제 버튼을 가운데 두려면 좌우에 둘씩 있어야 한다. v4에서 홈의 '자산 흐름 보기'가 소비분석으로 이어져 홈 옆에 둔 것으로 보인다. 그 결과 오른쪽은 실적관리 · 마이처럼 카드를 다루는 탭이 모였다 | 추정 |
| 마이가 맨 오른쪽 | 계정 · 설정을 끝자리에 두는 흔한 배치. 10/16 IA부터 그대로다 | 기록: `00-IA.png`, 이유는 추정 |

10/16의 '순환' 순서는 v4에서 깨졌다. 지금 순서를 따로 설명하는 기록이 없으니 팀이 이유를 정해 두면 좋다(5장).

### 1.7 햄버거 메뉴가 없는 이유

결정을 적은 기록은 없다. 10/22 회의록에 "컨설턴트님이 UI 요소의 의미(⋮ 점 3개, 햄버거 메뉴 등)까지 물어본 적이 있으니 화면으로 설명할 준비"라는 메모만 있다. 아래는 코드와 지침으로 맞춰 본 이유라 전체를 추정으로 둔다.

| 이유 | 근거 |
|---|---|
| 최상위 목적지가 탭 넷과 결제 버튼 하나로 하단 막대에 다 들어간다. Material 2 지침은 서랍 메뉴를 목적지가 다섯 개 이상이거나 계층이 깊을 때 권했다. 우리 화면은 탭 아래로 한두 단계다 | 지침: [Material 2 Navigation drawer](https://m2.material.io/components/navigation-drawer), 1.1 화면 지도 |
| 숨긴 메뉴는 덜 쓰인다. NN/g가 모바일에서 잰 결과 숨긴 내비게이션 사이트는 내비게이션을 쓴 비율이 44%, 보이는 메뉴를 섞은 사이트는 89%였다 | 비교: [NN/g, 2016](https://www.nngroup.com/articles/find-navigation-mobile-even-hamburger/) |

### 1.9 탭 화면과 흐름 화면

| | 탭 화면 `TabScreen` | 흐름 화면 `FlowScreen` |
|---|---|---|
| 바탕 | 회색 위 흰 카드(반경 20, 그림자 없음) | 흰 바탕. 상세 화면은 `cards = true`로 회색 위 카드 |
| 앱바 | 뒤로 없음. 왼쪽 제목(홈은 로고) + 오른쪽 알림 종 하나 | ← 또는 ✕(결제처럼 닫는 화면) + 제목. 오른쪽엔 그 화면의 일(+ 추가 · CSV 저장 · 모두 읽음 표시)만 |
| 아래 | 하단 탭 막대 | 보는 화면은 하단 탭 막대(고정 주 버튼이 있으면 그 위), 입력 · 확정 흐름은 고정 주 버튼(`BottomCta`, 56dp)만 |
| 단계 막대 | 없음 | 가입 4단계(이름까지) · 연결 2단계(막대만) |
| 코드 | `Containers.kt:141-159` | `Containers.kt:110-139` |

- 근거: 기록 01 §2 "탭 화면 = 회색 바탕 위 흰 카드, 등록 · 결제 · 설정 · 입력 흐름 = 흰 바탕".
- 하단 탭 막대는 11/15까지 탭 첫 화면 넷에서만 보였다. 화면마다 막대가 있다 없다 해서 11/16에 메인 그래프의 보는 화면(잔고예보 · 실적 상세 · 혜택 리포트 · 결제 내역 · 거래 상세 · 마이 하위 화면 등) 모두로 넓혔다(-521, `navigation/BottomBarRules.kt`).
- 숨기는 화면은 입력 · 확정 흐름뿐이다: 결제 코드 · 결제 완료 · 취소 코드, 이거 사도 될까 I-01~I-05, 예정 수입·지출 추가 · 수정, 카드 추가 · 카드 순서, 탈퇴, 간편 비밀번호 바꾸기. 가입 · 연결 · 잠금 해제 · 본인 확인은 메인 그래프 밖이라 원래 숨는다. 입력 도중 탭을 눌러 쓴 내용을 잃거나 결제 도중 다른 데로 새지 않게 하려는 것이다. 목록은 `BottomBarRulesTest`로 묶었다.
- 하위 화면에서 골라진 탭은 그 화면이 쌓인 탭이다. 마이에서 연 잔고예보는 마이, 홈에서 연 결제 내역은 홈이다. 하위 화면에서 탭을 누르면 지금 탭의 하위 화면을 저장 없이 닫고 바꾼다. 하위 화면째 저장하면 다른 탭 그래프의 화면이 엉뚱한 탭에 되살아나기 때문이다.
- 스낵바는 막대가 없는 흐름 화면에선 주 버튼 위로, 탭 첫 화면에선 가운데 원이 올라온 만큼 올린다. 막대가 있는 하위 화면은 고정 버튼(잔고예보 · 혜택 한도 등)이 있을 수 있어 그만큼 더 올린다(`YamuApp.kt`).

### 1.11 화면 전환

모든 화면 교체는 0.2초 페이드 하나다. 옆으로 밀거나 옮기지 않고 모션 줄이기에서는 0.15초(`YamuNavHost.kt:93-104`, `core/designsystem/theme/ScreenSwap.kt`). 라이브러리 기본(0.7초 남짓)은 금융 앱에서 굼뜨게 느껴졌다. 밀기 전환은 앞으로 · 뒤로가 섞인 우리 흐름(완료 화면이 흐름을 지우는 경우 등)에서 방향이 어긋난다고 봤다(기록: -320 커밋, 모션 명세 M-TOKENS. 밀기 이유는 추정).

## 8. 고칠 목록

효과는 사용자가 겪는 불편의 크기, 비용은 스토리 포인트(1pt = 1시간), 위험은 다른 화면 · 진행 중 작업과 부딪힐 가능성이다.

| 순위 | 묶음 | 담는 것 | 효과 | 비용 | 위험 |
|---|---|---|---|---|---|
| 1 | 찾기 쉬운 길 | V-01 · V-02 · V-03 | 높음 | 5pt | 낮음. 화면 추가 없이 입구만 |
| 2 | 화면 읽기 · 터치 | V-05 · V-08 · V-09 · V-10 · V-11 | 높음 | 7pt | 중간. 공용 부품(칩 · 작은 버튼) 높이가 바뀌면 여러 화면 배치가 움직인다 |
| 3 | 아이콘 · 문구 맞추기 | V-04 · V-07 · V-12 | 중간 | 4pt | 낮음 |
| 4 | 메인 색 · 판정 태그 색 확정 | V-06 · V-14 | 중간 | 1pt + 결정 | 결정이 먼저(팀 · 기획) |
| 5 | 실패 표시 통일 | V-13 | 낮음 | 3pt | 중간. 여러 화면의 상태 처리 |

11/16 사용자 승인으로 1~3을 Jira로 만들어 레인을 나눴다. 문서는 S15P31E103-515, 찾기 쉬운 길(레인 A)은 -516, 화면 읽기 · 터치(레인 B)는 -513, 아이콘 · 문구(레인 C)는 -514이고 머지 순서는 A → C → B다. 레인 A에서 '이거 사도 될까?'는 마이에서 열어도 잔고예보를 밑에 깔고 연다. 계획 저장 뒤 '잔고예보에서 보기'와 뒤로 가기가 지금 흐름 그대로 맞게 하려는 것이다. 4 · 5는 팀 결정과 일정을 기다린다.

V-02는 레인 A에서 잔고예보 앱바의 종을 톱니로 바꿔 풀었다. 같은 날 알림 설정 입구를 마이 한 곳으로 모으면서(-521) 그 톱니와 알림 화면의 톱니도 뺐고, 알림 화면의 '모두 읽음' 아이콘은 글자 '모두 읽음 표시'로 바꿨다.
