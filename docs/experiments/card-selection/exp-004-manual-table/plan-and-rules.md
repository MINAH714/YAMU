# EXP-004 승인 범위와 고정 규칙

목적은 정확한 혜택표와 현재 잔여 한도를 확인하는 수동 규칙을 기존 선택 전략과 비교하는 것이다. 사용자가 수정 요청과 구현·실행 승인을 제공했다. 앞선 ‘혜택이 1원이라도 있으면 우선 카드를 유지’ 제안은 철회했으며 실행하지 않았다. 이번에는 1원과 1,000원을 비교해 후자를 선택한다. 수정 계획 전문의 별도 과거 파일은 기록 미확인이다. 승인된 사용자 요구와 실제 실행 전 고정한 JSON을 구분해 보존한다.

실행 전 [혜택표 JSON](frozen-manual-table.json)을 작성하고 실행기가 어떤 결과 계산보다 먼저 별도 실행 폴더로 복사했다. 결과 확인 뒤 표·거래·규칙을 변경하지 않았다. 소비 10·15·25·50·75·100% × 2·3장, 총 12조건이다. 100%는 EXP-001/002, 나머지는 EXP-003에서 이어진다. 거래 24건의 시각·순서·가맹점·금액·사실, 카드 순서, 환산값, 초기 상태, 시드 0~99를 유지한다. 신규 정책·거래 사실 보완은 없다.

## 사람이 확인할 혜택표

등록 시드와 기존 모의 정책을 기준으로 한다. 실물 카드사의 최신 약관을 별도로 검증했다는 뜻이 아니다. 근거는 `be/seed/01-card-catalog.sql`, `02-card-catalog-ab20.sql`, `03-benefit-composition.sql` 및 각 실행의 prepared-policies.json이다. 정책과 코드의 전체 해시는 manifest.json에 있다.

| 카드 | 이번 거래의 대상·대표 혜택 | 최소 결제액·전월 실적 | 건·일·월 한도 및 공유 |
|---|---|---|---|
| 신한카드 처음 | 음식점·스타벅스·GS25·쿠팡 5% 포인트 | 0원·30만원 이상, 이번 전월 40만원 | 건 500P, 일 TODAY_DAILY 1,000P, 월 TODAY_MONTHLY 5,000P; 네 업종 공유 |
| KB국민 청춘대로 톡톡카드 | 스타벅스 50% 할인 | 0원·30만원 이상 | STARBUCKS 월 10,000원; 이 거래 범위에서 일·건 한도 없음 |
| LOCA LIKIT Eat | 음식점·커피 60% 할인 | 0원·40만원 이상 | ALL_MONTH 월 13,000원 공유; 이 거래 범위에서 일·건 한도 없음 |

톡톡의 버거 20%는 별도 월 5,000원이며 고정 거래 중 해당 거래가 없다. LOCA 배달·멤버십 60%는 같은 ALL_MONTH를 쓰지만 이번 음식점은 직접 구매, 쿠팡은 일반 상품 구매이므로 해당하지 않는다. 이 사실을 바꾸어 새 혜택을 만들지 않는다. 표 밖의 가맹점·조건은 0원으로 추정하지 않고 중단한다.

## 예상액과 선택

매 거래에서 현재 금액·가맹점·업종·채널, 확정된 일반 구매 사실, 전월 실적, 정상 결제 상태, 카드별 누적 한도 사용량을 확인한다. 처음의 이번 실적 구간은 30만원 이상 50만원 미만으로 고정한다. 모든 카드의 전월 실적은 400,000원, 당월 실적과 한도 사용량 0, 결제 가능 금액 각 10,000,000원, ACTIVE/NORMAL로 시작한다.

- 대상 조건과 실적을 만족하면 `금액 × 정률`에 건·일·월 잔여 한도의 최솟값을 적용한다. 이어 거래별 1단위 미만을 DOWN 절사한다. 처음은 1P=1원으로 환산한다. 추가 비용은 기존 모의 정책의 0원이다.
- 부분 잔여에서도 잘린 예상액을 다른 카드의 예상액과 비교한다. 완전 소진·확정된 비대상·실적 미달이면 정상 0원이다. 정보 누락은 예외로 중단한다.
- 가장 큰 예상액을 선택한다. 정확한 동률이면 기본 카드(처음), 기본 카드가 동률 후보가 아니면 처음→톡톡→LOCA 순서로 고른다. 모두 0원이면 기본 카드다.
- 이번 적용 범위에 정액 지급, 할인 후 기본 적립 전환, COUNT 한도, 한 거래의 동시 복수 혜택은 없다. 이를 임의로 생략한 것이 아니며, 별도 적용 대상이 생기면 표 밖 조건으로 보고 새 계획이 필요하다. 공유 한도는 포함한다.
- 다음 거래·미래 소비·월말 최적화는 사용하지 않는다. 현재 당월 실적 달성의 미래 가치도 수동 점수에 더하지 않는다. YAMU 자체의 기존 동률 규칙은 그대로 둔다.

선택 함수는 기존 계산기·추천기의 계산 결과를 받지 않는다. 고정 JSON과 현재 누적량으로 먼저 예상·선택한 뒤 기존 계산기로 후보별 실제 혜택을 감사하고 선택 카드만 정산한다. 실적·한도·결제 가능액은 기존 계산기의 확정 차감량으로 갱신한다. 예상액으로 공유 한도를 차감하지 않는다. 각 전략의 상태는 독립이다.

이 범위의 단순 정률·절사·공유 한도를 모두 표에 포함했으므로 의도한 근사 오차는 없다. 예상·실제 차이는 0으로 강제 보정하지 않고 별도 기록한다. 선택 결과가 YAMU와 같아도 규칙을 바꾸지 않는다.

## 검증·파일·보존

새 소스는 `CardSelectionManualTableTest.java`, `CardSelectionManualTableSupport.java`, `card-selection-exp-004.json`이다. 기존 테스트·입력·정책·서비스 구현은 수정하지 않는다. 문서는 이 디렉터리와 고유 실행 폴더에 추가하고 전체 README·record-audit.md에는 연결만 추가한다.

기존 전략은 재사용만 하지 않고 1,254회를 재실행한다. 원본 ZIP의 runs.json과 생성 DB ID·숫자 표현만 정규화해 거래·후보 평가·혜택·실적·한도를 모두 비교한다. 수동 12회를 추가한다. 랜덤은 같은 java.util.Random과 시드 0~99, 같은 카드 순서다.

초기/전체 소진/각 한도 최대−1·최대 상태에서 모든 거래·카드의 계산 가능성과 표 예상액을 확인한다. 1원 대 1,000원, 동률, 전체 0원, 절사, 실적 미달, 정보 부족 중단을 검사한다. 기존 계산기의 일 한도 다음 날짜 초기화와 대표 음식점·커피 거래도 검산한다. 등록 최소 결제액은 0이므로 양수 최소 결제액 경계는 해당 없음이다. COUNT·기본 적립 전환·동시 복수 혜택은 해당 없음으로 남긴다.

실패는 고유 실행 ID에 남기고 동일 조건 재실행과 조건 변경을 구분한다. 오류를 0원으로 숨기거나 원본을 교체하지 않는다. 이번 실행은 첫 시도 성공이며 조건 변경·재실행은 없었다.
