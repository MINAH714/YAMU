# EXP-001 — 두 카드 최소 실험

이 문서는 최초 실행 이후 보존 점검 시 작성한 과정 기록이다. 사전 계획과 승인은 해당 작업 채팅에 근거하며, 원본 파일처럼 소급 생성한 문서가 아니다.

## 목적·승인 범위

같은 보유 카드와 한 달 소비 내역에서 선택 방식별 총혜택 차이를 확인한다. 사용자가 카드 2~3종·거래 20~30건·랜덤 시드 100개·기존 계산기 사용을 요청했고, 처음·톡톡 2장과 구체적인 24건 계획을 승인했다. 기존 서비스 정책·미커밋 작업·Jira·외부 문서는 변경하지 않는 범위였다.

카드 선정은 혜택 계산뿐 아니라 당월 실적 인정·귀속월도 기존 규칙으로 확인할 수 있다는 이유였다. 처음은 음식점·카페·편의점·온라인쇼핑과 일/월 공유 한도를, 톡톡은 스타벅스 할인과 월 한도를 제공한다. ZERO·Mr.Life는 당시 확인한 실적 정보의 부족 때문에 선택하지 않았다. 실제 사용자 대표성이나 상품 약관 전체 검증을 주장하지 않았다.

## 고정 조건과 위치

- [원본 입력](frozen-input.json): 2026년 11월 2·6·11·16·21·27일, 각 날짜 12시 음식점·13시 스타벅스·17시 GS25·19시 쿠팡. 한국 시각 기준 24건·309,000원.
- 국내 일반 직접 구매·일시불·포인트 미사용·신규 유예 종료. 거래별 금액과 사실은 입력 및 ZIP의 prepared-policies.json에 있다.
- 전월 실적 각각 400,000원, 당월 실적·한도 사용량 0, 가용 신용한도 각각 10,000,000원, ACTIVE/NORMAL, 기본 카드 처음.
- 전략: 처음 고정, 톡톡 고정, 카페 톡톡/나머지 처음, YAMU, java.util.Random.nextInt(2)의 시드 0~99.
- 초기 상태는 같고 이후 실적·한도는 전략·시드별 독립 갱신. 상태 장부는 테스트 전용, 계산과 선택은 기존 구현 사용. 승인·청구 E2E가 아니다.
- [manifest](manifest.json)의 73개 파일 해시가 확장 착수 때 현재 파일과 모두 일치했다. 일부 구현은 미커밋 상태였다. [소스 보존본](source-overlay.zip), [소스 해시](source-checksums.json)를 함께 남긴다.

첫 두 실패의 전체 콘솔 로그·당시 입력 파일 원본·정확한 시작 시각은 기록 미확인이다. 실패 내용은 확인된 채팅과 보고서에서만 정리했으며 실패 파일을 역으로 만들어 원본이라고 표시하지 않았다. 최종 성공 XML 헤더는 점검 당시 tests=1, failures=0, errors=0, skipped=0, timestamp=2026-11-12T15:18:33.985Z, time=3.167초로 확인했다. XML 원본은 영구 보존하지 않았으므로 여기의 값은 관찰 기록이다.

## 결과와 확장 이유

처음 5,000원, 톡톡 10,000원, 랜덤 평균 12,736원, 업종 규칙과 YAMU 각각 15,000원. 랜덤 표준편차 2,066.82원, 최솟값 4,400원, 중앙값 13,475원, 5~95백분위 7,500~14,800원, 최댓값 15,000원. 96회가 YAMU보다 낮고 4회가 같았다.

최종 본 실행 4,992개 카드 평가에서 계산 불가 0건. 초기·전체 한도 소진 평가 각각 48개와 수식 검산을 통과했다. 이는 사전 입력 보완 후의 수치다. 첫 실험은 개별 한도 경계의 전 조합을 전수 검사한 것은 아니다.

두 전략 모두 관련 월 한도를 채웠다. 18번 스타벅스에서 YAMU가 처음으로 바꿔 얻은 400P는 다음 GS25의 적립 여력을 줄여 월 합계 차이가 없었다. 선정한 카드·소비 조건에 한정된 결과이며 자동 선택이 단순 규칙보다 항상 우월하다고 할 수 없다.

따라서 첫 확장은 거래를 그대로 두고 음식점·카페 공유 할인 한도를 가진 실제 등록 상품을 한 장 추가하는 것으로 정했다. [EXP-002](../exp-002-three-cards/README.md)에서 카드 추가 변화와 같은 세 카드에서의 선택 차이를 구분한다. 상세 재현 방법은 [색인](../README.md#재현)을 따른다.
