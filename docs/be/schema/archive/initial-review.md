# 초기 스키마 DDL 사전 검토안

작성일: 2026-10-22. 최종 정리: 2026-10-26. 상태: 검토 내용을 바탕으로 상세 컬럼 사전·DDL 초안 작성.

이 문서는 SQL 작성 전 논의를 남긴 검토 기록이다. SQL 초안과 컬럼 사전을 작성했으며 2026-10-26 브랜드 단위 변경 후 실제 MySQL에서 DB 테스트를 포함한 전체 30개 테스트가 생략 없이 통과했다. 최신 상세 설계와 검증 범위는 [현행 컬럼 사전](../dictionary.md)을 따른다. ‘확정’은 사용자와 합의한 내용이며 ‘제안’은 당시 검토한 설계안이다.

## 1. 산출물과 구현 계획

DDL 파일의 명칭은 **Flyway 버전 SQL 마이그레이션 파일**이다. 프로젝트는 MySQL 8.0, Java 17, Spring Boot 3.5, JPA `ddl-auto=validate`를 사용한다.

승인 후 작성한 파일:

- `be/src/main/resources/db/migration/V20261026_1__create_initial_schema.sql`: 23개 테이블, FK·UNIQUE·CHECK·인덱스·컬럼 설명.
- `docs/be/schema/dictionary.md`: 전체 컬럼 사전, 관계·인덱스 근거, 서비스 검증 책임, 미결 정책 목록.
- `be/src/test/java/com/yamu/be/global/schema/InitialSchemaMigrationTest.java`: 기존 `MySqlTestSupport`를 활용해 빈 MySQL에 마이그레이션을 적용하고 핵심 제약 위반을 확인한다.

기존 엔티티나 설정 변경은 현재 계획에 포함하지 않는다. 기존 공통 감사 시간 엔티티와 호환되는 컬럼을 만든다. 운영 DB에 적용하는 작업은 별도다.

## 2. 확인된 기준과 제안 타입

| 항목 | 기준·제안 | 담당자가 알아야 할 점 |
|---|---|---|
| PK / FK | `BIGINT` signed, 독립 엔티티 PK는 `AUTO_INCREMENT` | 프로젝트 JPA `Long`과 일치시킨다. FK의 타입과 부호를 통일한다. 연결 테이블 PK 구성은 컬럼 사전에서 명시한다. |
| 원화 금액 | `BIGINT signed`, 용도별 CHECK | BIGINT는 저장소 기준이며 signed는 Java Long과 범위를 맞추기 위한 제안. 결제 요청 금액은 `CHECK (amount > 0)`으로 양수만, 실적 합계·할인액·사용량은 `CHECK (amount >= 0)`으로 0과 양수를 허용한다. 현재 제안에서 음수 금액은 허용하지 않는다. |
| 비율 | 확정: `DECIMAL(9,6)`, 0~1 비율 | 10%는 `0.100000`으로 저장하며 FLOAT/DOUBLE의 근사 오차를 피한다. Java에서는 BigDecimal로 금액×비율을 계산하고, 혜택별 약관의 처리 방식·단위·시점에 따라 원 미만을 처리한 최종 원화 금액을 BIGINT로 저장한다. 절사·반올림 기준은 임의 선택하지 않고 약관을 조사한다. 미확인 기준의 모의 서비스 처리·표시 방식은 별도 결정한다. CARD_BENEFIT의 rounding_mode·rounding_unit·rounding_stage·application_timing과 조건 스냅샷에 당시 기준을 기록한다. 미확인 값은 NULL로 남긴다. |
| 포인트 | 확정: `DECIMAL(19,6)` | 금액과 포인트 단위는 분리한다. 원화 환산율과 계산 당시 결과를 함께 보존한다. |
| 발생 시각 | 확정: `TIMESTAMP(6)`, UTC | 결제·인증 등이 발생한 날짜와 시각을 저장한다. 애플리케이션·JDBC·DB 세션 시간대를 UTC로 통일한다. TIMESTAMP는 저장·조회 시 세션 시간대를 기준으로 변환하므로 연결별 시간대 설정을 유지한다. MySQL 8.0의 초 단위 표현 범위는 UTC 1970-01-01 00:00:01~2038-01-19 03:14:07이며, 현재 설계는 이 범위 안의 시각을 다룬다. |
| 실적·청구 기준 월 / 출금·환급 예정일 | 확정: `DATE` | 기준 월은 한국 달력 기준 해당 월 1일로 통일한다(예: 2026년 10월 실적 → 2026-10-01). 출금·환급 예정일은 시각 없이 날짜만 저장한다. 이 값들은 UTC 발생 시각으로 취급하지 않는다. 영업일 여부는 DATE 타입만으로 알 수 없으므로 별도 휴일 정보를 이용해 계산한다. |
| 상태·유형 | `VARCHAR` + 확정 코드 CHECK | JPA enum STRING 규칙을 따른다. 코드 길이는 전체 코드 목록을 보고 정한다. 미확정 상태 목록은 확정인 것처럼 제약에 넣지 않는다. |
| 외부 식별자 | 문자열, 길이·대소문자 규칙 확인 | userKey·계좌번호는 숫자 타입으로 바꾸지 않는다. 길이를 임의 확정하지 않는다. 금융망 인터페이스 문서 필요. 토큰·멱등키는 대소문자를 구분하는 정렬 규칙 검토. |
| 비밀·계좌 정보 | 확정: 암호화 값과 조회용 식별값 분리 | 계좌번호·userKey의 보관 범위와 암호화 책임은 추가 확인한다. 암호화 방식·키 관리·암호문 저장 길이는 아직 미확정이다. 임의의 짧은 VARCHAR에 암호문을 저장하지 않는다. 비밀번호 원문·생체 원본·단기 토큰 저장 금지. |
| 공개키 | 확정: TEXT + 알고리즘 정보 | 현재 공개키와 key_algorithm은 USER_DEVICE에 저장하고 키 교체 이력은 USER_DEVICE_EVENT에 남긴다. 세부 형식은 인증 구현 명세에 맞춘다. |
| 동시 수정 값 | `version BIGINT NOT NULL`, JPA `@Version` 대응 | 월별 실적·한도와 상태 변경 대상에 적용 검토. version 컬럼만으로 동시성은 해결되지 않으며 갱신 조건·재시도·트랜잭션이 필요하다. |
| 문자셋·엔진 | 확정: InnoDB / utf8mb4 | 일반 표시명과 토큰·멱등성 키 등 정확한 비교가 필요한 식별값의 정렬 규칙을 구분한다. |

MySQL CHECK는 8.0.16 이상에서 실제 강제된다. NOT NULL 없이 CHECK만 쓰면 NULL이 통과할 수 있다. 다른 행·테이블을 조회하는 CHECK는 지원하지 않으므로 기간 중첩·소유권·합계 정합성을 CHECK로 해결했다고 설명하지 않는다. [MySQL CHECK](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)

시각 타입의 범위와 변환 특성: [MySQL DATE / DATETIME / TIMESTAMP](https://dev.mysql.com/doc/refman/8.0/en/datetime.html).

## 3. 테이블별 저장 내용과 확인할 규칙

‘제약’은 잘못된 값이나 중복 기록이 저장되지 않도록 막는 규칙이다. 아래에는 각 테이블이 저장하는 내용과 지켜야 할 규칙을 정리했다. 이 표는 설계 검토용이며, 표를 쉽게 고쳐 쓴 것이 모든 규칙의 승인을 뜻하지는 않는다.

‘기존 정책’은 원본 문서에 정해진 내용이고, ‘제안’은 이번 DDL 검토에서 제시한 내용이다. 확정된 내용은 규칙 열에 남기며, 기능 구현 시 다룰 정책은 Notion에서 관리한다. 실제 컬럼 이름·길이·필수 여부는 전체 컬럼 사전에서 확정한다. 테이블 이름은 소문자와 밑줄을 사용하고, USER의 실제 DB 이름은 `app_user`를 제안한다.

| 테이블 | 무엇을 저장하나요? | 지키려는 규칙과 이유 |
|---|---|---|
| USER | 본인인증 정보, 휴대폰 암호문·조회용 해시, PIN 해시, 금융망 계정, 가입·탈퇴 상태 | **확정:** email·password_hash는 두지 않는다. 휴대폰 해시 + 생년월일 조합의 중복을 막는다. PIN은 해시로 저장하고 본인인증·PIN 변경·탈퇴 시각을 기록한다. PIN 분실 시 본인인증 후 새 PIN을 설정한다. |
| LINKED_ACCOUNT | 사용자, 계좌 정보, 연결 상태, 인증 기록 | **확정:** 1원 인증 후 조회한 본인 계좌 중 선택한 계좌를 연결한다. 재연결은 기존 기록을 재사용하고 status로 관리한다. |
| CARD_PRODUCT | 서버가 생성하는 내부 상품 번호(id), 카드사·상품명, 신용/체크 구분, 마감일 계산 일수 | **확정:** 같은 카드 상품을 중복 등록하지 못하게 한다. 상품은 내부 번호로 구분하며 외부 카드사 상품 코드를 필수로 사용하지 않는다. **기존 정책:** 결제일에서 상품에 저장한 일수(신한·국민·우리형 14일 / 하나형 13일 / 현대형 12일)를 빼 이번 청구에 포함할 이용기간의 마지막 날을 계산한다(POL-005). |
| USER_CARD | 사용자 보유 카드, 카드 상품, 출금 계좌, 결제일, 사용 상태 | **제안:** 다른 사용자 계좌를 출금 계좌로 지정하지 못하게 한다. **기존 정책:** seed 실적·혜택 사용량 초기화까지 성공해야 카드 등록을 완료한다. 필수 데이터 누락·초기화 실패는 등록 실패로 처리한다. 결제일 관련 계산은 POL-005를 따른다. |
| CARD_BENEFIT | 할인·적립 규칙, 해당 규칙의 버전과 적용 기간 | **확정:** 절사·반올림과 승인액·청구액 반영은 혜택별 약관을 따른다. **제안:** 같은 혜택의 같은 버전을 중복 저장하지 않는다. **기존 정책:** 규칙이 바뀌어도 과거 규칙은 남겨 이전 결제의 계산 근거를 보존한다. |
| BENEFIT_TARGET | 혜택이 적용되는 브랜드·업종과 거래별 적용·제외 조건 | **확정:** 약관의 제외 조건에 해당하면 혜택을 적용하지 않는다. BRAND 대상은 merchant_id FK로 연결한다. 온라인·백화점 입점 같은 조건은 CONDITION으로 기록하고 당시 거래 조건과 비교한다. 필요한 조건을 모르면 혜택을 임의 확정하지 않는다. 동일 대상 중복은 UNIQUE로 막는다. |
| MERCHANT | YAMU 서버가 생성하는 브랜드 단위 가맹점 번호(id), 브랜드명·코드, 업종 | **2026-10-26 확정:** 스타벅스처럼 브랜드마다 한 행으로 관리한다. brand_code는 필수·고유하다. 지점별 좌표·채널은 이 테이블에 두지 않는다. 지도 매장은 외부 정보로 연결하며 결제 채널·입점 시설은 거래별로 기록한다. |
| LIMIT_GROUP | 공유하는 혜택 한도, 규칙 버전, 일별·월별·결제 건별 구분, 금액·횟수 단위 | **제안:** 같은 한도 규칙의 같은 버전을 중복 저장하지 않는다. ‘월 1만원’과 ‘월 3회’는 서로 다른 단위로 계산한다. **기존 정책:** 과거 규칙은 보존한다. |
| BENEFIT_LIMIT_LINK | 어떤 혜택이 어떤 한도를 함께 사용하는지 | **제안:** 같은 혜택과 한도의 연결을 중복 저장하지 않는다. A 카드 혜택이 실수로 B 카드 한도를 사용하지 못하게 한다. |
| TIER_LIMIT | 전월 실적 구간별 한도 | **제안:** ‘30만원 이상 60만원 미만’처럼 경계를 정해 정확히 60만원인 거래가 두 구간에 동시에 들어가지 않게 한다. 최솟값이 최댓값보다 크거나 구간이 서로 겹치는 입력도 막는다. |
| PAYMENT_TRANSACTION | 결제 카드·가맹점·금액·상태, 요청 UUID(request_key), 실적 인정액과 기준 월, 취소 시각 | **확정:** POS가 새 결제 요청마다 UUID를 만들고 재시도에는 같은 값을 보낸다. request_key는 CHAR(36) NOT NULL UNIQUE로 저장해 모든 POS의 결제 요청을 통틀어 중복을 막는다. 같은 키·같은 요청이면 기존 처리 상태·결과를 반환하고, 금액·가맹점·사용자 등 요청 내용이 다르면 거절한다. **기존 정책:** 취소해도 결제 당시 실적 인정액은 기록에 남긴다. |
| PAYMENT_BENEFIT | 결제에 실제 적용한 할인·캐시백·포인트 결과와 적용 정책 버전 | **확정:** 결제 ID + 혜택 ID 조합에 UNIQUE를 걸어 같은 결제의 같은 혜택을 중복 저장하지 않는다. 서로 다른 혜택의 동시 적용 여부는 약관을 따른다. **기존 정책:** 이후 약관이 바뀌어도 당시 계산 근거를 보존한다. |
| PAYMENT_LIMIT_IMPACT | 결제 직전 남은 한도와 이번 결제가 차감한 금액·횟수, 사용 기준 날짜·월, 취소 복구 여부 | **제안:** 같은 결제의 같은 한도 사용 기록을 중복 저장하지 않는다. **기존 정책:** 전체 취소 시 원래 사용량만 한 번 복구한다. 사용량 변경과 복구 기록은 함께 성공하거나 함께 취소되도록 처리한다. 일별 사용 횟수는 결제별 혜택 기록과 승인·취소 이력으로 확인한다(FR-060). |
| CARD_MONTHLY_PERFORMANCE | 카드별 확정된 월간 실적 합계 | **제안:** 같은 카드의 같은 달 합계는 하나만 둔다. **기존 정책:** 등록 시 seed로 실적을 확정하며 신규 카드·확인된 무거래는 0원이다. 필수 seed 누락은 등록 실패로 처리한다. |
| MONTHLY_LIMIT_USAGE | 카드별·한도별 월간 사용 금액과 횟수 | **제안:** 같은 카드·한도·월의 합계는 하나만 둔다. **기존 정책:** 월별 사용량을 집계해 관리한다. 일별 사용 횟수는 별도 일별 합계 테이블을 우선 만들지 않고 거래 기록으로 확인한다(FR-060). |

## 4. 일반 FK만으로 해결되지 않는 관계

1. **소유자 일치**: USER_CARD / CARD_BILL / CASHFLOW_ITEM / REFUND의 계좌가 관련 사용자 소유인지 확인해야 한다. 가능한 관계에는 `(id, user_id)` UNIQUE와 복합 FK를 고려하고, 중복 컬럼이 과도한 경로는 서비스 트랜잭션 검증으로 명시한다.
2. **카드·상품 일치**: 거래 카드와 청구서 카드, 적용 혜택과 카드 상품, 한도 그룹과 카드 상품, 환급 회차와 원거래가 일치해야 한다.
3. **인증 근거**: LINKED_ACCOUNT가 참조한 로그가 동일 사용자의 성공 인증인지 확인해야 한다. 단기 challenge·토큰과 1회 소비는 Redis 책임이며 DB FK는 인증 성공을 증명하지 않는다.
4. **정책 기간**: 버전별 적용 기간과 실적 구간의 중복은 일반 UNIQUE로 막을 수 없다. 정책 변경 작업을 직렬화하고 중복 검증을 한다. POL-009의 다음 달 적용을 유지한다.
5. **취소 복구**: 거래 기록·한도 복구 표시·집계 차감을 하나의 트랜잭션으로 묶어야 한다. 복구 시각만 추가해도 중복 복구가 자동 방지되지는 않는다.

FK는 기본 RESTRICT 제안이다. 거래·감사 기록에 CASCADE DELETE를 일괄 적용하지 않는다. 탈퇴 시 삭제·익명화·보존 범위는 DEC-001 결정이 필요하다. MySQL FK는 즉시 검사하므로 부모를 먼저 생성하고 데이터를 입력한다. [MySQL FK](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html)

MySQL UNIQUE는 nullable 컬럼의 NULL을 여러 개 허용한다. 이 점을 선택적 1:1에는 활용할 수 있지만 중복방지 키에는 NOT NULL과 함께 사용해야 한다. [MySQL CREATE INDEX](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)

## 5. 검증 계획과 적용 시 주의

- 빈 Testcontainers MySQL에 실제 Flyway 적용, 업무 테이블 23개 및 FK 생성 확인.
- 중복 결제 키, 중복 회차·월 집계·알림 키, 잘못된 FK, 음수 금액·잘못된 월 입력 거절 확인.
- 선택적 관계의 NULL 허용과 UNIQUE 관계 확인. 소유권을 복합 FK로 설계한 경우 다른 사용자 계좌 연결 거절도 확인.
- 재실행 때 이미 적용한 버전이 다시 실행되지 않는지 확인.
- Docker가 없어 DB 테스트가 생략되면 성공으로 보고하지 않고 검증 미완료로 표시.
- 서비스 수준의 취소·출금·동시 결제 시나리오는 DDL 테스트로 보장되지 않는다. 각 기능 구현 때 별도 검증.
- 출금 응답을 받지 못하면 금융망 처리 상태를 먼저 확인한 뒤 응답·후속 처리를 결정한다. 이는 서버 구현 항목이며 추가 정책 결정 사항이 아니다. 확인 없이 실패로 단정하거나 중복 출금하지 않는다. 확정 실패에 대한 재출금은 기존 POL-007대로 지원하지 않는다.

MySQL DDL은 암묵적 COMMIT 때문에 파일 중간 실패 시 전체가 롤백된다고 보장할 수 없다. 실패하면 남은 테이블과 Flyway 이력을 확인하고 복구 절차를 결정한다. 기존 데이터 삭제나 `repair`를 자동 실행하지 않는다. [Flyway 트랜잭션 처리](https://documentation.red-gate.com/fd/migration-transaction-handling-273973399.html)

## 검증

2026-10-27 초기화 상태 컬럼 제거 후 실제 MySQL에서 InitialSchemaMigrationTest **16개 통과, 실패·오류·생략 0개**. 월간 실적·사용량의 명시적 0 저장, 필수값 누락·음수·중복 집계 거절을 확인했다. 카드 등록 서비스의 초기화·롤백 구현은 이 스키마 테스트 범위에 포함되지 않는다.

2026-10-27 공식 시작일 NULL 허용 변경 후 InitialSchemaMigrationTest를 재실행했다. 실제 MySQL에서 **15개 통과, 실패·오류·생략 0개**. 혜택·한도 모두 시작일 미확인 + 종료일 존재를 저장할 수 있고, 두 날짜가 알려진 경우 동일일·역순 기간이 거절되는지 확인했다. 현재 혜택 선택 서비스와 외부 약관 제공 여부 검증은 별도다.

`be`에서 `./gradlew.bat test` 실행. `InitialSchemaMigrationTest`는 MySqlTestSupport의 실제 MySQL 8.0 컨테이너에서 Flyway 적용·재실행·핵심 UNIQUE/CHECK/FK를 확인한다. Docker가 없으면 DB 테스트가 생략되며 실제 적용 검증 완료로 보고하지 않는다. 운영 DB에는 적용하지 않는다. MySQL DDL 중간 실패는 전체 롤백이 보장되지 않으므로 자동 clean/repair를 하지 않는다.

2026-10-26 브랜드 단위 변경 후 `./gradlew.bat test --rerun-tasks` 실행 결과: **30개 통과, 실패·오류·생략 0개**. 신규 스키마 테스트 14개, 기존 DB 테스트 3개, 일반 테스트 13개가 모두 실행됐다. 실제 MySQL 8.0에서 업무 테이블 23개 생성, Flyway 적용 이력·재실행 시 추가 적용 없음, 핵심 UNIQUE/CHECK/FK 거절, UTC 시각 저장·조회를 검증했다. 브랜드 코드 중복·존재하지 않는 브랜드 혜택 대상 거절, 같은 브랜드의 서로 다른 입점 시설 기록, 마스터 변경 후 당시 snapshot 유지, 미확인 거래 조건 보존·잘못된 채널 거절도 확인했다. DB 테스트는 서비스의 실제 혜택 판정·POS 인증·지도 매칭을 검증한 것이 아니다.

검증 중 보완: MySQL의 CHECK 위반(3819)·필수 컬럼 누락(1364)이 Spring에서 UncategorizedSQLException으로 전달되어, 특정 Java 예외 클래스 대신 실제 DB 제약 오류 코드로 판정하도록 테스트를 수정했다. 연결·문법 오류는 통과시키지 않는다. 테스트 클래스 사이 컨테이너 재시작 시 이전 DataSource를 재사용하지 않도록 신규 테스트의 Spring 컨텍스트를 분리했다. 서비스 수준의 동시 결제·취소 정산과 전체 JPA 업무 엔티티 매핑은 이 검증 범위에 포함되지 않는다.
