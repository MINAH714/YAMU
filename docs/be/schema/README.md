# YAMU DB 스키마 안내

스키마 문서는 이 폴더에서 관리한다. 먼저 리뷰 관점과 테이블을 읽는 순서를 확인한 뒤 컬럼 사전을 살펴본다. 관계·처리 흐름의 보충 설명은 테이블을 모두 읽은 뒤에 확인한다.

## 어떤 문서를 읽나요?

| 문서 | 독자와 목적 |
|---|---|
| [컬럼 사전](dictionary.md) | 사람·AI 공통. 23개 테이블의 컬럼·타입·NULL·기본값·키·제약과 컬럼별 설명 |
| [구현 지침](implementation.md) | 구현하는 개발자·AI. 서비스 검증, 동시성·재시도, 미확인 사항과 검증 방법 |
| [이전 검토 기록](archive/initial-review.md) | 과거 논의가 필요한 경우에만 조회. 현행 구현 기준으로 사용하지 않음 |

DB에서 실행할 구조는 [Flyway 마이그레이션 폴더](../../../be/src/main/resources/db/migration)의 SQL을 버전 순서대로 적용한 결과가 원본이다. 기능 정책은 Notion, 요청·응답 형식은 API 명세서에서 관리하며 이 폴더에서는 해당 위치를 연결한다. 미결정 정책을 문서 분리 과정에서 새로 확정하지 않는다.

## 리뷰할 때 볼 것

1. 필요한 데이터가 알맞은 테이블에 있는가? 특히 결제·혜택·한도·청구의 역할을 확인한다.
2. 해당 컬럼이 언제 채워지고, NULL과 0이 각각 무엇을 뜻하는가?
3. 중복·다른 사용자 데이터 연결은 DB가 막는가, 서비스가 검사하는가? 구현 책임은 [구현 지침](implementation.md)에 구분했다.

전체 타입과 제약을 외우기보다 담당 기능의 테이블을 [컬럼 사전](dictionary.md)에서 찾아 확인한다.

먼저 아래 순서로 [컬럼 사전](dictionary.md)의 테이블을 모두 살펴본다. 관계·처리 흐름에서 헷갈리기 쉬운 내용은 이 문서 맨 아래 「테이블을 모두 읽은 뒤 보는 보충 설명」에 모았으니 테이블 검토 후 읽는다.

## 확인된 범위

2026-10-27 기준 23개 테이블·286개 컬럼·FK 34개의 MD/SQL 정의를 대조했고, 계좌번호 끝 네 자리의 문서 이름을 SQL과 같은 `account_last4`로 통일했다. 격리 MySQL에서 스키마 테스트 17개를 포함한 전체 39개 테스트가 통과했으며 실패·오류·생략은 0개다. `payment_limit_usage`로 이름을 바꿔도 기존 사용량·복구 기록이 보존되는 것을 확인했다. 서비스 전체 구현이나 운영 DB 적용을 완료했다는 의미는 아니다. 실행 명령과 검증 범위는 [구현 지침](implementation.md)을 참고한다.

## 테이블을 모두 읽은 뒤 보는 보충 설명

아래 내용은 [컬럼 사전](dictionary.md)의 테이블을 모두 살펴본 뒤 읽는다. 결제·혜택·한도·청구 사이의 관계가 헷갈릴 때 참고한다.

### 결제 한 건의 처리 흐름

`payment_transaction`의 구조 :
**결제 요청을 처음 받으면 한 행을 INSERT하고, 이후에는 같은 행의 status와 관련 결과 컬럼을 UPDATE하는 구조**다.

예를 들어 결제 1024번이 승인된 뒤 취소되면 다음처럼 바뀐다. 아래는 시점별 모습이며, 네 행을 각각 저장한다는 뜻이 아니다.

```text
요청 접수: INSERT → 결제 1024 | status = REQUESTED
처리 시작: UPDATE → 결제 1024 | status = PROCESSING
승인 완료: UPDATE → 결제 1024 | status = APPROVED
취소 완료: UPDATE → 결제 1024 | status = CANCELED
```

승인이 거절되면 APPROVED 대신 DECLINED로 갱신한다. 이 테이블은 결제의 현재 상태와 결과를 저장한다.

### 혜택 결과·한도 사용·월간 합계의 관계

| 기록 | 예시 |
|---|---|
| `payment_benefit` — 실제 받은 혜택 | 결제 A에서 300원 할인 |
| `payment_limit_usage` — 결제별 한도 사용 | 결제 A가 금액 한도 300원과 횟수 한도 1회 차감. 서로 다른 한도 그룹이므로 두 행 |
| `monthly_limit_usage` — 월간 한도 사용 합계 | 같은 카드 & 한도 그룹의 10월 사용량 총 800원 |
| `card_monthly_performance` — 월간 실적 합계 | 같은 카드의 10월 실적 총 35만원 |

취소하면 해당 결제의 한도 사용량만 한 번 복구하고, 월간 한도 사용 합계와 월간 실적 합계를 모두 조정한다. 혜택 결과와 한도 사용량을 더해 같은 금액으로 계산하지 않는다.

### 결제와 계좌 출금의 관계

카드로 결제했다고 항상 그 순간 사용자 계좌에서 돈이 빠져나가는 것은 아니다. 체크카드는 결제할 때 출금하지만, 신용카드는 먼저 결제하고 나중에 결제일에 카드값을 낸다. 이 차이 때문에 출금 기록을 연결하는 테이블도 달라진다.

| 결제 방식 | 사용자 계좌에서 언제 출금하나요? | 성공한 출금의 금융망 거래 번호를 어디에 저장하나요? |
|---|---|---|
| 체크카드 | 결제 처리 과정에서 바로 출금 | 해당 결제 기록인 `payment_transaction.fin_transaction_no` |
| 신용카드 일시불 | 결제일에 해당 청구서의 카드값을 출금 | 청구서 기록인 `card_bill.fin_transaction_no` |
| 신용카드 할부 | 매달 결제일에 해당 회차 금액이 포함된 카드값을 출금 | 매달 해당 청구서의 `card_bill.fin_transaction_no` |

예를 들어 신용카드로 여러 번 결제해도 결제일에는 청구서에 모인 카드값을 출금한다. 따라서 그 출금 번호는 개별 결제가 아닌 청구서에 연결한다. `fin_transaction_no`는 금융망이 반환한 출금 거래 번호이며 결제 상태 코드가 아니다. 신용카드는 승인 완료 상태여도 `payment_transaction`의 이 값은 NULL이다.

여기서 출금은 사용자 계좌에서 돈이 빠져나가는 것을 말한다. 가맹점에 판매대금을 지급하는 정산은 YAMU 구현 범위에 없다.

### 청구서와 회차의 관계

`card_bill`은 청구서 한 장, `bill_item`은 그 안의 일시불 또는 할부 회차다. 청구서의 이용기간은 어느 날짜의 결제를 청구하는지 표시한다. `installment_months`는 일시불 1, 할부는 총 개월 수이며 현재 회차 번호가 아니다.

### 카드 등록 시 실적·한도 초기화

카드를 등록하자마자 전월 실적과 이번 달 남은 혜택 한도를 보여주려면, 등록 전에 사용한 거래도 계산에 포함해야 한다. YAMU에서는 실제 카드사 거래내역 대신 미리 준비한 모의 거래 데이터(seed)를 사용한다.

사용자가 카드를 등록하면 서버는 해당 카드의 모의 거래로 전월·당월 실적과 이번 달 혜택 한도 사용량을 계산해 저장한다. 이 작업까지 성공해야 사용자에게 등록 완료로 응답한다. 예를 들어 전월 실적이 35만원인 카드는 등록 직후에도 그 실적이 반영된다.

- 새로 발급해 거래가 없거나, 거래가 없다는 사실을 확인한 카드: 실적·한도 사용량을 0으로 저장한다.
- 있어야 할 모의 거래 자료가 누락됐거나 계산에 실패한 카드: 임의로 0을 넣지 않고 등록을 실패 처리한다. 등록 과정에서 일부만 저장된 내용도 되돌린다.

따라서 등록 완료된 카드의 실적·사용량을 별도로 ‘준비 중’이나 ‘확인 불가’로 표시하는 초기화 상태 컬럼은 두지 않는다. `user_card.status`의 `PENDING`은 서버에 미리 준비됐지만 사용자가 아직 등록하지 않은 카드라는 뜻이며, 실적 계산이 진행 중이라는 뜻이 아니다.

위 내용은 등록 서비스를 구현할 때 적용할 정책이다. 이번 초기 스키마 작업에는 서비스용 seed 데이터와 등록·초기화 서비스 구현이 포함되지 않았다.
