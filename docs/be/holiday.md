# 영업일 계산 (holiday)

영업일을 한 규칙으로 세도록 공통 계산기를 둡니다(`com.yamu.be.global.calendar`).
기준은 결제 정책 초안 4-3(POL-005·FR-067)과 10/21 결제 정책 회의입니다.

## 누가 무엇을 정하나

- **계산기는 날짜만 답합니다.** "이 날짜가 영업일인가?", "다음 영업일은 언제인가?"
- **청구 쪽**이 이 계산기를 불러 출금 예정일(`card_bill.withdrawal_date`)을 정합니다. 청구 출금일, 할부 회차 출금일, 환급 기한이 여기에 해당합니다.
- **잔고예보**는 출금일을 두 가지로 얻습니다.

| 경우 | 잔고예보가 쓰는 것 |
|---|---|
| 이미 생긴 청구(진행 중·확정·미납) | 청구 쪽이 정한 `withdrawalDate`를 `CardBillReader`로 **그대로** 읽습니다. 다시 계산하지 않습니다. |
| 아직 청구가 없는 날짜(가상 구매 `BillingSchedule`, 신용카드 예정 지출 `CreditWithdrawalSchedule`) | 잔고예보가 직접 계산하고, 영업일은 **이 계산기**(`businessDayOnOrAfter`)로 셉니다. 잔고예보의 `forecast.BusinessCalendar.onOrAfter`와 뜻이 같습니다. |

청구가 있으면 그 값을 그대로 쓰고, 없을 때도 같은 계산기로 영업일을 세서 청구 화면과 잔고예보 화면에 서로 다른 출금일이 나올 여지를 줄입니다.
이용기간 마감·결제일로 청구 월을 정하는 규칙은 지금 잔고예보 `BillingSchedule`에만 있습니다. 청구(`card_bill`)를 구현할 때 같은 규칙을 쓰도록 맞춥니다(Task 7.2.1, `CreditWithdrawalSchedule` 주석).

## 쓰는 법

`BusinessDayCalendar` 빈을 주입받아 씁니다. 날짜는 모두 **한국 날짜**(`LocalDate`)입니다. UTC 시각에서 날짜를 뽑을 때는 `ZoneId.of("Asia/Seoul")`로 바꾼 뒤 넘깁니다.

| 메서드 | 결과 | 예 |
|---|---|---|
| `isBusinessDay(date)` | 토·일·공휴일이 아니면 true | 2026-10-09(금, 한글날) → false |
| `businessDayOnOrAfter(date)` | 영업일이면 그날, 아니면 그 뒤 첫 영업일 | 2026-09-24(추석 연휴) → 2026-09-28(월) |
| `plusBusinessDays(date, n)` | 기준일은 세지 않고 다음 날부터 영업일을 n개 센 날. n은 1~366 | 2026-12-30(수) + 3 → 2027-01-05(화) |

```java
LocalDate withdrawalDate = calendar.businessDayOnOrAfter(paymentDate);   // 청구 출금일
LocalDate refundDueDate = calendar.plusBusinessDays(canceledOn, 3);      // 환급 기한
```

## 규칙

- **쉬는 날:** 토요일, 일요일, 공휴일(대체공휴일·선거일 포함)
- **노동절·제헌절:** 2026년부터 관공서 공휴일이라 쉬는 날입니다.
- **임시(1차):** 12월 31일처럼 관공서 공휴일이 아닌 날은 영업일로 셉니다.
- **데이터가 없는 해:** 주말만 쉬는 날로 계산하고, 경고 로그를 해마다 한 번 남깁니다.
- **데이터 파일이 하나도 없거나 깨졌을 때:** 배포 전에 잡습니다. 빌드 테스트(`EmbeddedHolidaysTest`)가 실제 파일을 읽어 누락·형식 오류를 확인합니다.
- **그래도 실행 환경에서 파일을 읽지 못했을 때:** 서버는 뜨고 에러 로그를 남깁니다. 영업일 계산이 필요한 작업만 `HolidayDataUnavailableException`으로 멈춥니다(API 응답은 500 `INTERNAL_ERROR`). 토·일은 데이터 없이도 확실하므로 `isBusinessDay`가 그대로 `false`입니다.
  - 빈 공휴일 목록으로 대신 계산하지 않습니다. 그러면 평일에 낀 공휴일을 영업일로 잘못 세서 틀린 출금일이 저장됩니다.

### 데이터가 없는 해를 오류로 보지 않는 이유

다음 해 공휴일은 전년도 6월쯤 「월력요항」으로 발표됩니다(2027년은 2026-06-29). 그래서 2027년 1~6월에 12개월 할부로 결제하면 마지막 회차의 2028년 공휴일은 API 동기화가 있어도 **아직 어디에도 없습니다.** 파일을 읽지 못한 것은 문제라 계산을 멈추지만, 해가 빈 것은 정상적으로 생기는 일이라 주말만 빼고 계산합니다.

그 결과로 발표 전 해의 날짜로 미리 계산한 출금일은 **예정일**입니다. 미리 저장한 출금일(예: 할부 미래 회차의 `card_bill.withdrawal_date`)은 청구를 확정할 때 `businessDayOnOrAfter`로 다시 계산해야 합니다(청구 확정, 5.2.4). 확정할 때쯤에는 그 해 데이터가 들어와 있습니다.

## 공휴일 데이터

계산기는 **내장 파일과 공휴일 API 목록을 합친 것(합집합)**을 씁니다(`MergedHolidays`).

| 출처 | 위치 | 갱신 |
|---|---|---|
| 내장 파일 | `be/src/main/resources/holidays/{연도}.json` (2026·2027) | 사람이 고쳐 배포. 출처는 각 파일의 `source` |
| 공휴일 API | Redis `holiday:{연도}` → 서버 메모리 | 동기화 작업이 매일 받음(아래) |

- **API에만 있는 날**(임시공휴일 등)은 쉬는 날로 더해집니다.
- **내장 파일에만 있는 날**도 쉬는 날로 그대로 둡니다. 노동절·제헌절(2026년부터 관공서 공휴일)을 API가 반영하는지 아직 몰라서입니다. 통째로 바꾸면 빠진 날이 영업일이 되어 공휴일에 출금일이 잡힙니다.
  - 한계: 지정이 취소된 공휴일은 API로 지울 수 없습니다. 그때는 내장 파일을 고칩니다. 틀려도 출금이 하루 늦어지는 쪽입니다.
  - 둘이 다르면 동기화할 때 로그가 남습니다. `내장 파일에만 있는 공휴일이 있습니다`(warn)가 보이면 그 날이 정말 공휴일인지 확인합니다.
- 내장 파일을 읽지 못했어도 그 해 API 목록이 있으면 그것으로 셉니다. 둘 다 없으면 위 규칙대로 멈춥니다.

## 공휴일 API 동기화

공공데이터포털 「한국천문연구원_특일 정보」의 `getRestDeInfo`를 부릅니다(`HolidaySyncJob`, `HolidayApiClient`).

| 언제 | 하는 일 |
|---|---|
| 서버가 다 뜬 뒤 1회 | Redis에 있는 올해·내년 목록을 메모리로 읽고, 동기화한 적 없는 해만 API로 받습니다. 서버 시작을 붙잡지 않도록 따로 돕니다. |
| 매일 04:00(한국) | 올해·내년을 다시 받습니다. 청구 확정(00:30) 뒤, 청구 출금(07:00) 전입니다. |

- 한 해는 1~12월을 따로 불러 합칩니다. 응답은 XML로 읽습니다.
- **한 달이라도 실패하면 그 해는 덮어쓰지 않습니다.** 바로 다시 부르지 않고 다음 날 04:00에 다시 받습니다. 그동안은 기존 Redis 목록·내장 파일로 셉니다.
- **0건인 해**는 아직 발표 전(월력요항은 전년도 6월쯤)으로 보고 저장하지 않습니다.
- 같은 날 공휴일이 둘이면(어린이날·부처님오신날) 이름을 합쳐 하나로 둡니다. `isHoliday=N`(기념일)은 뺍니다.
- 서버가 여러 대여도 Redis 잠금(`holiday:sync:lock`)으로 하나만 부릅니다.
- Redis 목록에는 만료가 없습니다. 동기화가 계속 실패해도 마지막으로 받은 목록을 씁니다.

### 키 넣기

1. 공공데이터포털에서 「한국천문연구원_특일 정보」를 활용 신청하고 **디코딩 키**를 받습니다. 인코딩 키를 넣으면 두 번 인코딩되어 실패합니다.
2. 로컬: `application-local.yml`의 `yamu.holiday.service-key`. 운영: 서버의 `infra/.env.prod`에 `DATA_GO_KR_SERVICE_KEY`를 적습니다. `infra/compose.prod.yml`이 backend 환경변수로 넘깁니다(비어 있어도 서버는 뜸). CD는 서버에 복사해 둔 compose(`/opt/yamu/cd/`)를 쓰므로, compose를 바꾼 뒤에는 그 사본도 교체해야 반영됩니다(docs/infra/jenkins-cd.md).
3. 키가 비어 있으면 서버는 뜨고, 시작할 때 경고(`공휴일 동기화를 하지 않습니다`)만 남긴 뒤 내장 파일로 셉니다.
4. 키와 응답 본문은 로그에 남기지 않습니다. 실패 로그에는 연도·월·결과 코드·예외 종류만 나옵니다.

### 확인

```bash
redis-cli HGETALL holiday:2026
redis-cli GET holiday:2026:synced-at
```

| 로그 | 뜻 |
|---|---|
| `2026년 공휴일 N일을 동기화했습니다` | 정상 |
| `공휴일 동기화에 실패해 기존 데이터를 그대로 씁니다: … resultCode=…` / `returnReasonCode=30` | API 오류. `30`은 등록되지 않은 키입니다(활용 신청 직후에는 반영까지 시간이 걸립니다). |
| `공휴일이 API에 아직 없습니다(발표 전)` | 내년 공휴일 발표 전. 정상 |

### 아직 정하지 않은 것

- 공휴일이 바뀌었을 때 **이미 확정된 청구서의 출금일**을 다시 계산할지는 결제일 출금(5.4.3)에서 정합니다.
- JSON 지원·일일 호출 한도·임시공휴일 반영 시점은 실제 키로 확인한 뒤 여기에 적습니다.

### 새 해 파일 추가하기

1. 「월력요항」이 발표되면 `{연도}.json`을 추가합니다. 일요일과 겹친 공휴일도 넣고, `source`에 보도자료 링크와 합계(일요일 수 + 일요일이 아닌 공휴일 수 = 발표된 실질 공휴일 수)를 적습니다.
2. `EmbeddedHolidaysTest`에 그 해의 날짜 목록 테스트(`공휴일_{연도}년은_...`)와 72일 테스트의 연도·합계를 추가합니다. 이미 있는 해의 테스트는 고치지 않아도 통과합니다.
3. 이미 있는 해의 공휴일이 바뀌면(임시공휴일 지정 등) 그 해 파일과 날짜 목록 테스트를 같이 고칩니다. 임시공휴일은 API 동기화로도 들어오지만, 서버가 API를 못 부르는 경우를 위해 파일도 맞춥니다.
