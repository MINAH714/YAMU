# 잔고예보 (forecast)

선택한 계좌의 현재 잔액에 예정 수입·지출과 카드 청구 출금을 날짜별로 더해 앞으로의 잔액을 계산하는 기능입니다(`com.yamu.be.forecast`).
계좌마다 따로 계산한 뒤 같은 날짜끼리 합하므로, 계좌별 수치를 더하면 항상 통합 수치와 같습니다(FR-039).

| Task | 내용 | MR | 상태 (2026-10-30) |
|---|---|---|---|
| 7.1.4 (S15P31E103-66) | 계산 엔진, 예정 항목 변환, 잔액·청구 조회 계약, 서비스 | !45 | 리뷰 중 |
| 7.1.5 (S15P31E103-70) | 생활비 추정, 보수적 선, 잔액 부족 구간·위험 상태 탐지, 생활비 상세 | (!45 위에 쌓음) | 작업 중. 원천 연결·Controller는 후속 MR |

- 명세: 팀 노션 API 명세서 V2 「잔고예보 조회」 `GET /api/forecasts/balance`, 「생활비 예측 상세」 `GET /api/forecasts/living-cost`, 요구사항 정의서 V2 FR-033~041·045·046·064, DEC-008
- 계산 원칙: 팀 노션 「YAMU 잔고예보 계산 원칙 설계 (Task 7.1.1)」, 「잔고예보 복수 계좌·통합→상세 변경 내역 (2026-10-26)」
- 예정 항목: [cashflow.md](cashflow.md)

## 계산

### 기간
- 시작은 한국 날짜 오늘(주입한 `Clock` + `Asia/Seoul`), 끝은 시작 + 일수(끝 날 포함)입니다.
- `until=DAYS`면 `days`는 7·14·30입니다.
- `until=NEXT_INCOME`(기본)은 다음 수입일을 정할 잔고예보 설정 API가 아직 없어, 명세의 대체 규칙대로 30일로 계산합니다. 응답의 `horizon.type`은 실제로 계산한 `DAYS`입니다.

### 선
- `confirmed`(확정 선): 확정 입출금만 더합니다.
- `expected`(예상 선): 확정 + 예상 입출금을 더합니다.
- `conservative`(보수적 선): 예상 선에서 추정 하루 생활비를 **내일부터 그날까지** 날마다 뺍니다. 오늘 쓴 돈은 현재 잔액에 이미 들어 있어 빼지 않습니다(7.1.1 설계의 τ = t0+1부터). 생활비 자료가 없는 계좌는 null이고, 한 계좌라도 null이면 통합 보수적 선도 null입니다(일부만 더한 값을 주지 않음).
- 각 점은 그날 입출금을 모두 반영한 일말 잔액입니다. **기간의 모든 날짜에 점이 있습니다**(7.1.5에서 "입출금 있는 날만"에서 바꿈). 보수적 선은 날마다 줄어들어, 입출금 있는 날만 두면 최저점(다음 입금 전날)을 놓치기 때문입니다.
- 계좌별 선도 같은 날짜를 모두 가집니다. 그날 입출금이 없는 계좌는 직전 잔액입니다. 그래서 같은 날짜의 계좌별 값을 더하면 통합 값과 같습니다(FR-039).

### 무엇을 언제 어느 계좌에서
| 입력 | 계좌 | 날짜 | 선 |
|---|---|---|---|
| 현재 잔액 | 선택 계좌 | 시작값 | – |
| 계좌 지정 예정 수입·지출 | 그 계좌 | 예정일(`date`) | 확정 |
| 체크카드 예정 지출 | 카드 출금 계좌 | 예정일 | 확정 |
| 신용카드 예정 지출 | 카드 출금 계좌 | 청구 출금일(`CreditWithdrawalSchedule`) | 확정 |
| 확정 청구(`CONFIRMED`) | 확정 당시 출금 계좌 | 출금 예정일. 지났으면 오늘 | 확정 |
| 진행 중 청구(`ACCUMULATING`) | 카드의 현재 출금 계좌 | 출금 예정일 | 예상 |

- 오늘이 예정일인 **지출**은 뺍니다. 이미 빠졌다면 잔액을 적게 볼 뿐이라, 부족 위험을 놓치지 않는 쪽입니다.
- 오늘이 예정일인 **수입**은 더하지 않고 `excluded`로 알립니다. 이미 들어왔다면 두 번 더해 잔액을 부풀리고 부족 위험을 가리기 때문입니다. 오늘 거래가 잔액에 반영됐는지 가릴 근거(금융망 거래내역)가 아직 없습니다.
- 예정 항목은 확정(`CONFIRMED`) 항목만 읽습니다. 탐지 후보(`CANDIDATE`)는 만드는 기능이 아직 없어 읽지 않습니다.

### 빼는 것
| 경우 | 처리 |
|---|---|
| 실제 결제와 연결된 회차(`Entry.paid`) | 뺌. 실제 결제·청구 데이터가 대신함(DEC-008) |
| 선택하지 않은 계좌에 귀속 | 뺌. 이 예보의 범위가 아니라 알리지 않음 |
| 기간 밖으로 미뤄진 신용카드 출금 | 뺌 |
| 금액 미정(`amount=NULL`) | 차감하지 않고 `excluded`에 `AMOUNT_UNKNOWN` |
| 출금 계좌가 없는 카드, 계좌·카드가 모두 없는 행 | `excluded`에 `NO_WITHDRAWAL_ACCOUNT` |
| 없거나 등록 해제된 카드 | `excluded`에 `CARD_UNAVAILABLE`. 예보 전체를 실패시키지 않음 |
| 오늘이 예정일인 수입 | `excluded`에 `TODAY_INCOME_UNVERIFIED` |
| 오늘보다 앞선 날짜의 카드 예정 지출 | 읽지 않음. 아래 「지난 카드 예정 지출」 참고 |
| 다른 계좌의 청구(계약상 오지 않음) | 선택 계좌에 옮겨 담지 않고 뺌 |
| 미납 청구(`UNPAID`) | 차감하지 않고 `excluded`에 `UNPAID_BILL`(청구 ID·미납액·원래 출금일) |

### 카드 청구
BE 2가 확인한 상태별 규칙입니다(2026-10-30, !45 리뷰). 금액은 모두 실제로 출금될 금액이고, 출금일은 결제일이 비영업일이면 이미 다음 영업일로 옮긴 값입니다(POL-005).

| 상태 | 예보 | 금액 | 출금 계좌 |
|---|---|---|---|
| `ACCUMULATING` 이용기간 진행 중 | 출금일에 예상 선부터 차감 | 지금까지 쌓인 회차 합계 − 예상 청구할인 | 카드의 현재 출금 계좌 |
| `CONFIRMED` 청구 확정 | 출금일에 확정 선부터 차감 | 확정 청구액. 확정 뒤 결제를 취소해도 줄지 않고 환급으로 따로 처리 | 확정 당시 출금 계좌 |
| `PAID` 출금 완료 | 오지 않음. 이미 현재 잔액에 반영 | – | – |
| `UNPAID` 출금 실패·미납 | 차감하지 않고 `excluded`로 알림. 재출금 일정이 없음(FR-069 미정) | 남은 미납액 | 확정 당시 출금 계좌 |

- 결제일 07:00 출금 요청 뒤 결과가 확정되기 전(금융망 결과 불명 포함)에는 청구가 `CONFIRMED`로 남습니다. 출금일이 지났어도 오므로 **오늘 확정 선에서 뺍니다**. 예보 시작일 이전 날짜는 계산에서 버려지기 때문에 옮기지 않으면 빠집니다.
- 그 사이 실제로는 은행에서 이미 빠져 현재 잔액에 반영됐을 수 있어, 이 경우 두 번 빠진 만큼 잔액을 적게 봅니다. 부족 위험을 놓치는 쪽보다 낫다고 봤습니다.
- 진행 중 청구의 출금일이 지났으면 계약 위반이라 예보 전체를 실패시킵니다(음수 금액과 같음).

### 지난 카드 예정 지출
신용카드 예정 지출은 사용일이 예보 기간 안인 회차만 읽습니다. 사용일이 어제이고 출금일이 다음 주인 예정 지출은 넣지 않습니다.

- 이 시스템에서 카드로 실제 쓴 돈은 모두 `payment_transaction`(YAMU 결제·SEED)을 거쳐 `bill_item`, 즉 카드 청구에 들어갑니다.
- 그래서 지난 날짜의 카드 예정 지출은 둘 중 하나입니다.
  - 실제로 결제했다 → 이미 청구(`CardBillReader`)에 들어 있으므로, 넣으면 두 번 차감됩니다.
  - 결제하지 않았다 → 일어나지 않은 지출입니다.
- 둘을 가리는 근거는 사용자가 확인한 결제 연결뿐이고, 날짜·금액만으로 자동 매칭하지 않습니다(implementation.md 106행). 그래서 조회 범위를 출금일 기준으로 넓히지 않았습니다.
- YAMU 밖에서 같은 카드를 쓴 금액을 받아오게 되면 다시 봐야 합니다.

## 생활비 추정 (7.1.5)

명세 「생활비 예측 상세」의 AVG_3M(최근 완료 3개월 단순 평균)입니다. 7.1.1 설계안의 "최근 28일 평균"은 합의 전 제안이라, 그 뒤에 정해진 명세를 따랐습니다.

- **어느 달**: 한국 날짜 오늘 기준으로 이번 달을 뺀 지난 3개월 중, 거래를 빠짐없이 확인한(`complete=true`) 달만 씁니다.
  - `complete=true`이고 0원이면 실제로 0원 쓴 달이라 평균에 넣습니다.
  - `complete=false`이거나 행이 없는 달은 자료 누락이라 빼고, 그만큼 `confidence`가 내려갑니다.
- **REAL/SEED를 섞지 않음**(7.1.1 정책): 한 계좌에 다 확인한 실제 거래(REAL) 달이 하나라도 있으면 REAL 달만 쓰고, 없을 때만 모의 소비(SEED) 달을 씁니다. `dataOrigin`은 쓴 쪽입니다.
- **일평균** = 쓴 달들의 합 ÷ 그 달들의 실제 일수(2월·윤년 반영), **월평균** = 합 ÷ 달 수. 모두 원 단위 반올림입니다. 월평균 ÷ 30이 아닙니다. 명세 예시도 2026-10-30에 이 산식에 맞게 고쳤습니다(7·8·9월 217,000·217,000·210,000원 → 일평균 7,000원, 월평균 214,667원).
- **confidence**: 쓴 달이 3개면 HIGH, 2개면 MEDIUM, 1개면 LOW, 0개면 INSUFFICIENT(평균 null).
- **예상 생활비**(`projectedAmount`) = 일평균 × 예보 일수.
- **paceCheck**: 이번 달 행이 complete이고 평소 일평균이 0원이 아닐 때만, 이번 달 오늘까지 하루 평균이 평소의 1.3배를 **넘으면** `flagged`입니다(정확히 1.3배는 아님). 계산할 수 없으면 null입니다.
- **통합**: 계좌별 값의 합입니다. 계좌 귀속이 없는 소비를 여러 계좌에 복제하거나 나눠 담지 않습니다. 한 계좌라도 자료가 없으면 통합 평균은 null(INSUFFICIENT)이고, 통합 `confidence`는 가장 낮은 계좌 값입니다. REAL 계좌와 SEED 계좌를 함께 고르면 통합 `dataOrigin`을 SEED로 표시해 모의 소비가 들어 있음을 알립니다(계좌 하나 안에서는 섞지 않음).

### 생활비 원천 계약 (`LivingCostReader`)
- 계좌·월·출처(REAL/SEED)마다 행 하나: 그달 유효 생활 소비 합계(이번 달은 오늘까지)와 `complete`.
- **정제된 데이터만 준다**: 같은 소비가 체크카드 결제와 계좌 출금에 두 번 잡히면 한 번으로 줄이고(중복 제거), 소비 분류가 LIVING으로 끝난 것만 더합니다. 정기 지출(월세·통신비·구독료), 신용카드 청구, 본인 계좌 간 이체, 큰 일회성 지출, 목적을 알 수 없는 출금은 뺍니다.
- 음수 합계나 같은 계좌·월·출처 행이 두 번 오면 계약 위반으로 실패합니다(500). 오류 메시지에는 계좌·월·소비액을 넣지 않습니다(전역 예외 로그에 남기 때문). 선택하지 않은 계좌의 행은 무시합니다.
- **중복 제거·분류의 실제 구현은 아직 없습니다.** 원천 연동 단계(후속 MR)의 미완료 작업입니다.

## 위험 판단 (7.1.5)

- **안전 잔액**(`alertThreshold`): 명세의 현행 가정 100,000원을 생성자 인자로 받습니다(설정값·잔고예보 설정 API는 후속).
- **날마다 위험 수준**(선 기준): 그날 안전 잔액 **미만**인 가장 확실한 선(확정 > 예상 > 보수적)을 찾습니다. 확정 선이면 DANGER, 예상·보수적 선이면 WARNING, 미만인 선이 없으면 SAFE. 안전 잔액과 같은 금액은 SAFE입니다(FR-043 "임계값 아래").
- **위험 구간**(`riskWindows`): 그 선이 같은 날짜가 이어지면 한 구간입니다. 위험 수준이나 **선이 바뀌면** 구간을 나눕니다. 그래서 예상 선 미달이 이어지다 생활비 때문에만 미달인 날로 넘어가면, 같은 WARNING이라도 구간이 둘로 나뉩니다. 구간마다 부족액·최저일·원인이 한 선 기준으로 맞습니다.
  - `line`: 구간의 선(확정·예상·보수적).
  - `lowestBalance`·`shortfall`: 그 선의 구간 최저 잔액과, 안전 잔액까지 모자라는 금액.
  - `causes`: 그 선에 반영된 구간 안 출금만 넣습니다. 확정 선 구간은 확정 출금만(진행 중 청구 같은 예상 출금은 확정 선에 없으므로 뺌), 예상·보수적 선 구간은 확정·예상 출금. 보수적 선 구간은 생활비 추정 때문에 미달이 된 날들이라 `LIVING_COST_ESTIMATE`를 더하고, 금액·날짜는 그 구간 최저일까지 누적한 추정 생활비입니다.
- **요약**(`summary`)
  - `aggregateStatus`: 통합 선만 본 수준.
  - `status`: 통합·계좌별 수준 중 가장 나쁜 것. 통합이 안전해도 위험한 계좌가 있으면 그 수준입니다(최소 WARNING, 명세).
  - `hasAccountRisk`·`atRiskAccountCount`: SAFE가 아닌 계좌가 있는지, 몇 개인지.
  - `minBalance`·`minBalanceDate`·`endBalance`: 가장 나쁜 선(보수적, 없으면 예상) 기준. 최저가 같으면 이른 날.
  - `largestOutflow`: 통합 출금 합이 가장 큰 날("예정 출금 합계"). 출금이 없으면 null.
- 생활비 자료가 없어 보수적 선이 null이면 확정·예상 선으로만 판단합니다.

## 생활비 상세 (`LivingCostForecast`, 7.1.5)

명세 「생활비 예측 상세」 응답 모양입니다(`ForecastService.livingCost`).

- 잔액을 읽지 않으므로 계좌마다 `AccountQueryService.requireConnectedAccount`로 소유·연결을 확인합니다(남의·해제 계좌 404, 원천을 읽기 전).
- 기간(`period`)은 잔고예보 기본 기간(30일, `basis=DAYS`)입니다.
- `sources`는 평균에 쓴 달별 합계(계좌 합), `excluded`는 생활비에서 빼는 소비 종류 안내 3종(RECURRING·CREDIT_PAYMENT·UNCLASSIFIED), `dailyTarget`은 잔고예보 설정 API가 없어 null입니다.
- 선택한 **어느 계좌에도** 생활비 자료가 없으면 0원으로 확정하지 않고 422 `DATA_INSUFFICIENT`입니다. 일부 계좌만 없으면 200이고, 통합 평균은 null(INSUFFICIENT), 계좌별 값은 `accountLivingCosts`(자세히 보기)에서 보입니다.

## 청구 일정 계산 (`BillingSchedule`, 7.2.1)

카드 결제 한 건이 계좌에서 빠지는 회차별 날짜·금액을 계산합니다(Jira S15P31E103-131). DB를 읽거나 쓰지 않아 예상 일정이 실제 결제·청구서에 저장되지 않습니다. 가상 구매 시뮬레이션(7.2.2)과 잔고예보의 신용카드 예정 지출(`CreditWithdrawalSchedule`)이 쓸 계산입니다.

**계산 규칙**
1. 체크카드: 구매일에 한 번 바로 빠집니다. 구매일이 주말·공휴일이어도 그날입니다.
2. 신용카드 첫 청구 월(POL-005): 이용기간 마감일 = 그달 결제일 − N일(달력으로 거꾸로 셈). 구매 달부터 보면서 "구매일 ≤ 마감일"이 되는 첫 달입니다. 예: 결제일 14일·N=14면 2027-03-14 청구의 마감일은 2/28, 윤년 2028-03-14는 2/29입니다.
3. 회차별 청구 월: k번째 회차는 첫 청구 월에서 k−1달 뒤입니다(POL-013, 2~12개월).
4. 그 청구 월의 **원래 결제일**을 만든 뒤 비영업일이면 다음 영업일로 옮깁니다. 이전 회차의 실제 출금일에서 한 달을 더하지 않습니다. 옮긴 날이 다음 달이어도 청구 월은 바뀌지 않습니다.
   - 예(명세): 10/24에 120만 원 3개월, 결제일 14일 → 11/14(토)→11/16, 12/14, 1/14에 40만 원씩
5. 할부 금액은 똑같이 나누고 원 단위 나머지는 마지막 회차에 붙입니다(수수료 0원). 회차 합계는 항상 입력 금액과 같고, 나누기만 해서 큰 금액도 넘치지 않습니다.

**입력 계약**
| 입력 | 뜻·범위 | 근거 |
|---|---|---|
| `amount` | **승인 금액**: 즉시할인은 부르는 쪽이 이미 뺀 값, 청구할인은 반영 전. 회차마다 1원 이상(할부 개월 수 이상), 상한 없음 | 명세 「가상 구매 시뮬레이션」: 체크카드는 즉시할인 뺀 금액이 구매일에, 신용 할부는 청구할인이 있어도 회차를 원금대로 나눔. 청구할인은 청구 단위로 BE 2 청구가 뺌(「카드 청구」의 ACCUMULATING 금액) |
| `installmentMonths` | 일시불 1, 할부 2~12. 체크카드는 1만 | POL-013 |
| `paymentDay` | 신용카드 결제일 1~27 | 명세 「카드 등록」「카드 정보 수정」(FR-067), 카드 API·페르소나 시드도 1~27. DB 제약(1~31)보다 좁지만 모든 달에 있는 날이라 말일 보정이 필요 없음 |
| `billingCutoffDays` | 이용기간 마감 일수 N, 1~31. null이면 14 | 청구서 명세 "1차 14일", 시드 상품은 모두 null. DB 제약은 0 초과뿐이라 한 달을 넘는 비정상 값만 막음 |

- 계산이 성립하지 않는 값(위 범위 밖, 체크카드 할부, 신용카드 결제일 없음, 0원 회차가 생기는 금액)은 `IllegalArgumentException`입니다.
- 나머지는 마지막 회차입니다(현행 명세 「결제 승인 요청」「청구서 상세」 "POL-013 확정"). 옛 API 목록과 개인 노션 복사본의 "1회차에 더함(가정, DEC-007)"은 POL-013으로 대체됐습니다.
- **할부 5만 원 이상 같은 결제 조건 검증은 여기서 하지 않습니다.** 결제 쪽 조건 검증(BE 2 `PaymentTerms`, 아직 MR 전)이 할인 전 원래 결제 금액으로 하고, 7.2.2는 그 검증을 거친 뒤 이 계산을 부릅니다. 여기서 승인 금액으로 다시 보면 즉시할인 때문에 5만 원 아래로 내려간 정상 할부를 잘못 거절하고, 같은 규칙이 두 곳에 생깁니다.
- 할인 계산은 하지 않습니다. 체크카드 즉시할인은 부르는 쪽(7.2.2의 혜택 계산)이 금액에서 빼서 넘기고, 신용카드 청구할인·할부 회차별 할인을 시뮬레이션에 어떻게 보일지는 7.2.2에서 정합니다.

**영업일 달력 (`BusinessCalendar`)**
- "그날이 영업일이면 그날, 아니면 다음 영업일"을 돌려주는 계약만 있습니다. 영업일은 월~금에서 공휴일·임시공휴일을 뺀 날입니다(결제 정책 회의).
- **실제 구현체는 아직 develop에 없습니다.** BE 2의 공통 달력 `global.calendar.BusinessDayCalendar`(-210, !67)가 같은 기능(`businessDayOnOrAfter`)을 제공합니다. !67이 머지되면 이 인터페이스를 지우고 그 메서드를 주입합니다(이윤서 님 !60 리뷰). 그 전까지 테스트는 주말과 지정한 공휴일만 건너뛰는 가짜 달력을 씁니다.
- 카드 청구 출금일(BE 2)과 같은 달력을 써야 같은 청구의 출금일이 청구서 화면과 예보·시뮬레이션에서 달라지지 않습니다.
- 달력이 받은 날보다 앞선 날이나 null을 주면 계약 위반으로 `IllegalStateException`입니다.

**한계**
- 결제일을 바꾸면 지금 결제일로만 계산합니다. 명세 「청구서 목록」은 "결제일을 바꾸면 다음 청구서부터 적용, 진행 중 청구서는 그대로"라서, 결제일을 바꾼 직후 구매의 첫 회차가 청구서와 다를 수 있습니다. 예: 11/1에 14일→25일로 바꾸고 11/5에 사면 청구서는 12/14 출금, 이 계산은 11/25 출금. 진행 중 청구서(`ACCUMULATING`) 데이터가 생기면(-205·-200) 첫 회차는 그 청구서의 출금일을 쓰도록 BE 2와 맞춥니다.
- 청구서 생성(BE 2, -200)도 같은 규칙을 써야 하므로, 그 작업에서 `payment.billing` 같은 공용 위치로 옮기고 이용기간 마감일도 돌려주도록 합니다(이윤서 님 !60 리뷰). 쓰는 곳이 하나인 지금은 forecast에 둡니다.
- 잔고예보에는 아직 연결하지 않았습니다(아래 「미완료·한계」).

## 동시 요청·재시도

- 읽기만 하고 DB에 쓰지 않아 잠금이 없습니다. 같은 요청을 다시 보내도 결과만 다시 계산합니다.
- 잔액·생활비는 금융망을 부를 수 있어 예정 항목(DB)을 읽기 전에 따로 읽습니다. 둘 중 하나라도 실패하면 DB를 읽지 않고 끝납니다.
- 잔액 캐시(10분)와 `refresh`는 BE 1이 맡습니다. 잔고예보는 `refresh`를 그대로 넘깁니다.
- 잔액·예정 항목·청구는 한 시점에 함께 읽지 않습니다. 그 사이에 예정 항목이 바뀌면 그 요청에는 반영되지 않을 수 있습니다.

## 결정과 이유

| 결정 | 이유 | 고르지 않은 방법 |
|---|---|---|
| 계좌별로 계산한 뒤 날짜별 합 | 통합 잔액이 충분해도 특정 계좌 출금 부족이 가려지지 않게 하고, 상세와 통합 수치를 항상 일치시킴 | 잔액을 합친 뒤 한 번에 계산 |
| 원천은 조회 계약으로 받고 테스트는 가짜 데이터 | BE 1·BE 2 영역을 합의 없이 구현하지 않음 | 잔고예보 패키지에 Mock 공급자, 담당자 구현까지 보류 |
| 컨트롤러·빈 등록은 원천이 붙을 때 | 구현 없는 계약을 쓰는 빈은 서버를 못 띄움. 자리만 차지하는 운영 코드를 넣지 않음 | 원천이 없으면 422를 던지는 임시 구현 |
| 신용카드 예정 지출은 청구 출금일로 옮김 | FR-036·064: 신용카드는 승인일이 아니라 결제일에 계좌에서 빠짐 | 예정일 차감, 예보에서 제외 |
| 결제일 계산은 7.2.1에서 | 가상 구매와 같은 계산이라 한 번만 만듦 | 7.1.4에서 먼저 구현 |
| 오늘 지출은 빼고, 오늘 수입은 더하지 않고 알림 | 반영 여부를 모를 때 잔액을 적게 보는 쪽으로만 틀리게 함. 결제 연결 회차는 이미 빠짐 | 오늘 회차 모두 포함(수입 중복으로 위험을 가림), 모두 제외(오늘 출금을 놓침), 예상 선에만 반영 |
| 계좌별 선에 통합 선의 모든 날짜 | 응답만 보고 같은 날짜 합계를 대조할 수 있음 | 입출금 있는 날만 두고 "직전 값을 이어 쓴다"는 계약 |
| 지난 카드 예정 지출은 읽지 않음 | 실제 사용은 청구에 들어 있어 넣으면 중복 | 출금일 기준으로 조회 범위 확장 |
| 출금일이 지난 확정 청구는 오늘 확정 선에서 뺌 | 결과 불명인 출금을 놓치면 부족 위험을 가림 | 예상 선에만 반영(실제 실패 때 확정 선에 위험이 안 보임) |
| 미납 청구는 빼지 않고 `excluded`로 알림 | 재출금 일정이 없어 날짜를 만들 수 없지만, 갚을 돈이 남았다는 것은 알려야 함 | 조용히 제외 |
| 빼는 항목은 `excluded`로 알림 | 금액 미정을 0원처럼 계산하지 않고, 예보가 완전한 확정 잔액처럼 보이지 않게 함(implementation.md 103행) | 출금 계좌가 없으면 422로 예보 전체 실패 |
| 응답은 구현한 범위만 | 값이 없는 필드를 정상 응답처럼 보이게 하지 않음 | 명세 필드 전체에 null·빈 배열 |
| 날짜 선은 매일 점 (7.1.5) | 보수적 선이 날마다 줄어 최저점을 놓치지 않고 탐지가 단순함 | 입출금 날 + 최저점 날만 |
| 위험 수준은 선 기준 (7.1.5) | 명세의 "확정·예상·보수적 선 원칙"에 가깝고, 확실한 위험과 예측 위험을 구분 | 0원 미만 DANGER·기준 미만 WARNING(금액 기준) |
| 일평균 = 합 ÷ 실제 일수 (7.1.5) | 달마다 일수 차이(28~31일)를 반영. 명세 예시도 이 산식에 맞춤(2026-10-30) | 월평균 ÷ 30(명세의 옛 예시) |
| 생활비 자료가 없으면 보수적 선 null (7.1.5) | 0원 생활비를 정상 예측처럼 보이지 않게 함(명세) | 예상 선과 같은 값 + 부족 표시 |
| `complete`로 0원과 누락 구분 (7.1.5) | 실제로 안 쓴 달은 평균을 내려야 하고, 모르는 달은 빼야 함 | 행이 없으면 0원으로 봄 |
| REAL 우선, 없을 때만 SEED (7.1.5) | 한 계좌 안에서 실제·모의 소비를 섞지 않는 7.1.1 정책을 지키면서 자료를 덜 버림 | 섞이면 INSUFFICIENT |
| 위험 구간은 위험 수준이나 기준선이 바뀌면 나눔 (7.1.5) | 확실한 부족과 예측 부족을 따로 보여 주고, 구간마다 부족액·최저일·원인을 한 선으로 맞춤(리뷰 반영) | 기준 미만이 이어지면 한 구간, 위험 수준만으로 나누고 생활비 원인을 따로 계산 |
| 생활비 계약 위반 오류에 값을 넣지 않음 (7.1.5) | 예외 메시지가 전역 예외 로그에 남아 계좌·월·소비액이 기록되지 않게 함 | 디버깅용으로 행 전체를 메시지에 넣기 |
| 생활비 원천 실패는 예보 전체 실패 (7.1.5) | 누락을 숨기지 않는다는 명세 원칙 | 보수적 선만 비우고 계속 |

## 미완료·한계

- **API 없음**: 원천 구현 전이라 컨트롤러가 없고 `ForecastService`는 빈이 아닙니다. 앱에서 호출해 확인하지 못했습니다. 안전 잔액도 설정값이 아니라 생성자 인자입니다.
- **생활비 원천 미구현 (7.1.5 후속)**: `LivingCostReader` 구현, 체크카드 결제와 계좌 출금의 중복 제거, 소비 분류(LIVING) 판정, 데이터 완전성(`complete`) 판정이 모두 없습니다. BE 1(계좌 거래내역)·BE 2(결제) 원천과 함께 후속 MR에서 만듭니다. 그때까지 7.1.5는 완료가 아닙니다.
- **생활비 예측 상세 API·잔고예보 조회 API**: 컨트롤러는 원천 연결과 함께 후속 MR입니다.
- **잔액 부족 알림(FR-043)**: 위험을 판단만 하고 알림은 만들지 않습니다.
- **신용카드 예정 지출**: 출금일 계산(`BillingSchedule`, 7.2.1)은 만들었지만 아직 `CreditWithdrawalSchedule`로 연결하지 않아 예보에 들어가지 않습니다. 연결에 필요한 것: !59 머지(카드 정보 `UserCardRef`), 영업일 달력 구현체, 결제일이 없는 신용카드(시드 등)의 예정 지출을 `excluded`로 뺄 이유.
- **기간 밖**: 신용카드 사용일이 기간 안이어도 출금일이 기간 밖이면 빠집니다(`beyondHorizon` 미구현).
- **선택 계좌 수 상한 없음**: 명세는 "최대 개수 정책 위반 → 400"이라고만 하고 숫자를 정하지 않았습니다. 지금은 외부 입구(컨트롤러)가 없어, 컨트롤러를 붙이는 MR에서 명세 담당과 숫자를 정해 요청 경계에서 막습니다.
- **오늘 수입**: 실제로 아직 안 들어온 오늘 월급도 예보에서 빠집니다(`excluded`로 알림). 금융망 거래내역으로 반영 여부를 가릴 수 있게 되면 다시 봅니다.
- **결제 연결 전 중복**: 사용자가 예정 지출과 실제 결제를 연결하지 않으면, 같은 지출이 예정 지출과 카드 청구에 함께 반영될 수 있습니다. 날짜·금액만으로 자동 제외하지 않는 정책(implementation.md 106행)을 따랐습니다.
- **정지·만료 카드**: 등록 상태만 보고, 카드사 정지·만료 여부는 예보에서 따로 거르지 않습니다.
- **결과 불명 청구 이중 차감**: 출금일이 지난 확정 청구가 실제로는 이미 빠졌다면 두 번 뺍니다(위 「카드 청구」).
- **BE 2 확인 대기**: 지난 할부의 다음 회차가 진행 중 청구 금액에 미리 들어가는지, 쓴 게 없는 카드도 0원 진행 중 청구로 오는지.
- **같은 날 입출금 순서**: 일말 잔액만 계산하므로, 같은 날 입금 전에 출금이 먼저 시도되는 경우의 실패 여부는 알 수 없습니다.
