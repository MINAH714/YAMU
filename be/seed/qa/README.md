# QA 페르소나 전달 패키지 — S15P31E103-442

담당 범위는 설계·생성 코드·검증·인프라 전달이다. 이 작업에서 SSAFY 회원/계좌 생성, 입출금, 실제 RDS 적재는 실행하지 않는다.
추천 엔진 전용 정책/시나리오는 S15P31E103-441에서 관리한다. 여기서는 현재 카탈로그를 읽고 QA 계정과 원장을 구성한다.

v3 세 사용자·IBK나라사랑카드 구성은 [IBK-551](IBK-551.md)을 따릅니다. 아래 기존 5종 구성은 v1/v2 기준입니다.

550의 동일 생활 이력 3인 구성은 [LIFE 전달 문서](LIFE-HANDOFF.md)와 `life-persona-1/2/3.example.json`을 사용합니다. 시작 잔액 225만 원, 원거래 기반 청구, 실제 시작 자금과 합성 원장의 전환 검증은 이 별도 LIFE 시나리오에만 적용됩니다. [월별 수치 보고서](LIFE-VALIDATION.txt)는 오프라인 `planQaLife`로 재생성합니다.

기존 세 운영 QA 계정을 실제 입출금 없이 준비하는 명시 도구는 [계정 준비 안내](ACCOUNT-PREPARATION.md)를 따릅니다. 이 경로에서는 `BILLING_JOBS_ENABLED=false`를 유지하며, 아래 일반 QA 환경의 배치 허용 절차를 적용하지 않습니다. 실제 기기 증명·PIN·BE 검토 전에 운영 준비를 실행하지 않습니다.

## 구성과 기대 결과

기준일 D는 입력의 baseDate(한국 날짜), 거래 시각은 UTC로 저장한다. 표의 기대값은 초기 상태 기준이다.
모든 계정은 카드 3장(체크: KB국민 노리 체크, 신용: 신한카드 처음·Mr.Life), 금융망 계좌 2개를 사용한다.
처음·체크는 계좌 0, Mr.Life는 계좌 1이다. 신용 결제일은 견본에서 15일이다.

| key | 목적 | 입력/원장 기대값 | 화면 확인 |
|---|---|---|---|
| rich | 기본 풍부형 | 최근 완료 6개월+당월 체크 소비(하루 3건), 신용 전월 실적 각각 400,000원, 당월 월납 혜택 1,500원 사용 | 홈·카드·거래 페이지·업종/월별 리포트·예보·알림 |
| empty | 빈 상태형 | 거래·혜택·청구·가계부·알림 0건, 3장 모두 7개 월 실적 0원 | 빈 목록과 데이터 부족 안내; 가입/기기 기록은 존재 |
| boundary | 경계형 | 처음 전월 299,999원, Mr.Life 전월 300,000원, 당월 Mr.Life 월납 3,000원 전부 사용 | 30만 원 기준 미달/달성, 월납 잔여 0원. 카드 전체 혜택이 소진된 뜻은 아님 |
| shortfall | 잔고 부족형 | 계좌 0 잔액 100,000원, D+2 월세 700,000원, D+10 급여 2,500,000원 | D+2에 계좌 0의 확정 잔액이 음수. AI 예보 금액·최초 경고일은 별도 확인 |
| states | 거래 상태형 | 기본 이력+90만 원 3개월 할부, 12,000원 취소, 8,000원 거절 | 승인/취소/거절 배지, 할부 원금 30만 원×3회, 청구 확정·출금·취소 환급 |

- 비어 있지 않은 계정의 가입 후 보강: 예정 항목 5개(급여·월세·구독·금액 미정·긴 제목), 알림 24개(읽음 12/미읽음 12).
- 가계부는 규칙과 첫 발생 건을 함께 만든다. 월 반복 회차는 기존 서비스가 조회/확장한다.
- 현재 월 신용 거래·할부 거래와 states의 전월 1일 취소 거래에 청구 회차를 만든다. 과거 6개월 소비 이력을 금융망 입출금으로 재현하지 않는다.
- 기존 등록 전 소비와 마찬가지로 과거 SEED 거래는 실적용 모의 이력이다. 전 거래의 과거 혜택을 재계산하는 추천 엔진이 아니다.
- 당월 Mr.Life SKT 월납 15,000원→1,500원 할인(경계형은 30,000원→3,000원)을 원장·건별/일별/월별 한도 기록에 함께 넣는다.
- 취소·거절은 실적 합계에서 제외한다. 취소 행은 원승인액을 보존한다.
- 일반 청구는 ACCUMULATING/PENDING으로 시작한다. 회차 금액은 현행 `BillItem.pending`과 동일하게 수수료 0원·청구액=원금으로 생성한다. 별도 카드사 수수료 정책을 추가한 것은 아니다.
- states의 12,000원 취소 건은 청구 확정 후 출금 전 취소 상태(CONFIRMED / REFUND_PENDING / 환급 PENDING·기한 없음)다. 출금 성공 후 환급 기한이 정해지고 환급 배치가 입금한다. 은행 요청/거래 번호와 납부·환급 완료 이력은 생성하지 않는다.
- SEED 거래는 취소 API의 실행 대상이 아니다. 실제 결제·취소 QA는 정상 POS 결제로 새 YAMU 거래를 만들어 수행한다.

## 인프라 준비 요청

1. 이 브랜치의 새 마이그레이션까지 적용된 QA DB와 카드 카탈로그를 준비한다. CLI는 DDL/Flyway를 실행하지 않는다.
2. 기존 `seed/01-card-catalog.sql`, `seed/02-card-catalog-ab20.sql`의 해당 상품·가맹점·정책이 필요하다.
   운영 카탈로그를 덮어쓰지 말고 선행 적재 여부를 확인한다. 카드 이미지는 기존 이미지 시드/배포를 따른다.
3. 페르소나마다 전용 SSAFY 회원 1명과 수시입출금 계좌 2개를 만든다. 다른 사용자와 계좌를 공유하지 않는다.
4. 초기 잔액: rich/empty/boundary/states는 계좌별 3,000,000원, shortfall은 계좌 0=100,000원·계좌 1=3,000,000원.
   이 금액은 화면용 시나리오 입력이며 서비스 정책이 아니다. 가입 1원 인증 후 QA 시작 시점 잔액을 다시 확인한다.
5. 현재 서버와 같은 암호화·조회 해시 키를 프로세스 환경변수로 공급한다. 키를 새로 생성하지 않는다.
6. `personas.example.json`을 `personas.local.json`으로 복사하고 금융망 값·테스트 본인인증 정보·카드 모의 번호를 채운다.
   견본의 회원/계좌는 실제 자원이 아니다. `REPLACE_WITH_SSAFY_USER_KEY`가 남으면 DB 명령은 거절한다.
7. QA 전용 계좌에서 청구·출금·환급 배치 및 수동 실행을 허용한다. 영구 격리 설정은 필요 없다.
   apply/enrich/reset/purge 실행 중에만 해당 QA 사용자 쓰기와 관련 작업을 잠시 멈추고, 완료 후 재개한다.
   공유 환경의 수동 실행은 `userId`로 QA 사용자만 지정한다. 스케줄 활성화는 환경의 기존 운영 방식을 따른다.

## 실행 순서 (be 폴더)

환경변수 목록은 [environment.example.txt](environment.example.txt)를 참고한다. 실제 비밀값을 명령행 인자로 넘기지 않는다.
PowerShell은 `.\gradlew.bat`, Linux는 `./gradlew`를 사용한다.

```powershell
# 오프라인 계획: DB나 금융망에 연결하지 않는다. 견본으로도 수량을 미리 볼 수 있다.
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=plan '-PqaFile=seed/qa/personas.example.json'

# 1. QA 접속/작업을 멈춘 뒤 가입 전 사용자·카드·소비/실적/한도 생성
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=apply

# 2. 앱을 켜서 정상 본인인증→계좌 연결→PIN→기기 등록→카드 3장 등록.
#    계좌 두 개 모두 연결하고 QA 가입 세션을 종료한다.

# 3. QA 접속/작업을 다시 멈춘 뒤 연결된 계좌에 예정 내역·청구·알림 보강
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=enrich

# 4. 원장 합계 검사 및 계정별 데이터 건수 확인
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=verify
```

모든 쓰기 명령은 `QA_SEED_MAINTENANCE=true`가 필요하다. 서버/외부 작업을 자동 정지시키지는 않는다.
실패 시 종료 코드 1, 성공 0. SQL/파서의 원문 예외는 비밀값 노출을 막기 위해 출력하지 않는다.
기본 파일은 `seed/qa/personas.local.json`; 다른 담당자 세트는 별도 datasetKey와 외부 회원/계좌를 사용한다.
원본 설정 파일은 삭제/초기화 때도 필요하므로 비밀 저장소에 보관한다.

## 청구·출금·환급 QA 실행

인프라가 정상 가입과 enrich를 완료한 뒤 기존 운영 API를 사용한다. CLI 자체는 금융망을 호출하지 않는다.

- 경로: `POST /api/admin/jobs/{jobName}/run`. 기존 관리자 인증을 사용하고 비밀 키를 문서에 기록하지 않는다.
- 요청 예: `{"userId":123,"dryRun":true}`. 123은 inspect로 확인한 QA userId로 바꾼다. 대상 확인 후 같은 요청의 dryRun을 false로 바꿔 실행한다.
- 순서: `bill-confirm` → `bill-withdraw` → `refund-payout`. 각 실행 결과와 inspect 상태, 금융망 계좌 거래내역을 대조한다.
- asOf 생략 시 현재 시각이다. 미래 asOf는 거절된다. 일반 청구는 이용기간 종료 후 확정, 출금 예정일 이후 출금된다. 날짜 제한을 SQL 수정으로 우회하지 않는다.
- 견본 D=2026-11-12·결제일 15일·마감 14일 기준: 당월 월납 일반 청구는 확정 가능하고 출금일은 11/16이다. rich의 15,000원 월납은 할인 1,500원 반영 후 13,500원 청구다.
- states의 별도 12,000원 취소 청구는 지난 출금 예정일을 가진 미처리 건이므로 즉시 출금→환급을 시험할 수 있다. 출금 전에는 환급이 실행되지 않는다. 성공 시 12,000원 출금, 같은 전용 계좌로 12,000원 환급이며 기한은 실제 출금일+3영업일이다.
- 재실행해도 완료 건에서 중복 출금·환급이 없어야 한다. 결과 불명이면 기존 작업의 거래내역 확인 흐름으로 해결한다.
- shortfall의 낮은 잔액은 예보 검증용이다. 출금 잔액 부족까지 보려면 실행 대상 청구 계좌의 잔액을 청구액 미만으로 준비하고 UNPAID를 확인한다. UNPAID는 자동 재출금 대상이 아니므로 새 시나리오는 초기화 후 시작한다.
- 실제 취소 API까지 검증하려면 POS에서 새 YAMU 거래를 만든다. 확정 전 취소는 청구 제외, 확정 후 취소는 출금·환급 흐름을 확인한다. SEED 원거래 취소 제한은 기존 서비스 정책 그대로다.

## 반복 실행·초기화·삭제

- `apply`: 같은 입력이면 현재 QA 진행 상태를 보존한다. 같은 datasetKey로 날짜/계정/카드 등 입력이 바뀌면 거절한다.
- `enrich`: 계정 모두 정상 가입·카드 등록 후 실행한다. 일부 계정 준비가 안 됐으면 전체 보강을 롤백한다. 완료 계정은 재보강하지 않는다.
- `reset`: 원본 입력으로 QA 세트를 삭제·재생성한다. ACTIVE도 QA 소유권이 있으면 초기화한다. **PIN·기기·계좌 연결도 초기화되어 다시 가입해야 한다.**
- `purge`: 등록된 QA 사용자와 테스트 도중 생긴 종속 데이터까지 삭제한다. 공용 상품·정책·가맹점과 다른 사용자는 보존한다. 이미 삭제된 세트는 성공 처리한다.
- 사용자 이름/전화번호 접두어나 `source=SEED`로 삭제 대상을 추측하지 않는다. DB 소유권 등록만 사용한다.
- 전체 세트가 한 트랜잭션이다. FK 확인을 끄지 않으며 지원하지 않는 새 참조가 생기면 전체 롤백한다.
- DB별 MySQL advisory lock으로 CLI 동시 실행을 막는다. 앱 쓰기와의 경합은 유지보수 시간으로 막아야 한다.
- 진행 중 결제·결과 불명 금융 요청은 삭제를 막는다. 먼저 결과를 확인하고 정상 상태로 해결한다.
- 월이 바뀌면 원본 파일로 purge 후 새 기준일 파일로 apply한다. 시드가 매일 자동 갱신되지는 않는다.

```powershell
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=inspect
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=reset
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=purge
```

`inspect`는 삭제 전 사용자별 종속 행 건수·기기 ID와 청구/환급 ID·연결 계좌 ID·상태·금액·금융망 요청/거래 번호를 보여 주는 읽기 전용 명령이다. 계좌번호와 userKey는 출력하지 않는다.
RDS 삭제와 금융망/Redis 정리는 별개다. 이 CLI는 금융망·Redis를 호출하지 않는다.
초기화 담당자는 다음 순서로 처리한다.

1. 대상 QA 사용자의 앱 요청·배치·수동 작업을 잠시 멈추고 실행 중 요청의 완료를 기다린다.
2. inspect 결과를 접근 제한된 작업 기록에 보관하고 금융망 거래내역과 대조한다. 결과 불명 요청은 먼저 기존 서비스의 조회·정산 흐름으로 확정한다. 요청 번호를 지워 강제로 삭제하지 않는다. 확정된 미납(UNPAID/CANCELED)·환급 계좌 없음(FAILED)은 삭제 가능하다.
3. 원본 입력으로 reset한다. DB 기록만 초기화되며 금융망에서 발생한 출금·입금은 취소되지 않는다. 초기화 직후 사용자는 PENDING이고 다시 정상 가입·계좌 연결·카드 등록이 필요하다.
4. 인프라가 각 전용 계좌의 **현재 금융망 잔액과 목표 초기 잔액의 차액**만 입출금해 복원한다. 300만 원을 매번 더 입금하거나 과거 시드 거래를 금융망에서 재실행하지 않는다. 기존 금융망 거래내역은 남는다.
5. 금융망 거래내역까지 새로 시작하려면 원본 입력으로 purge하고 인프라가 새 QA 회원/계좌를 준비한 뒤 새 바인딩으로 apply한다. 다른 사용자와 공유한 계좌는 사용하지 않는다.
6. 삭제 전 기록한 기기 ID의 refresh 세션과 QA 사용자 세션·계좌 잔액/결제 캐시를 기존 운영 절차로 정리한다. 재가입의 1원 인증 이후 목표 잔액을 다시 확인하고 enrich→verify 후 요청·배치를 재개한다.

v1을 이미 적재했다면 **기존 version=1 원본 파일로 inspect→purge**한 뒤 version=2 입력으로 apply→정상 가입→enrich한다. version만 바꿔 기존 dataset에 덮어쓰면 입력 해시 검사로 거절된다. v1의 apply/enrich/reset은 지원하지 않는다. 아직 적재하지 않았다면 v2 견본으로 바로 시작한다.
공유 Redis에 FLUSHDB/FLUSHALL을 실행하지 않는다. 자동증가 ID를 재사용하거나 초기화하지 않는다.

로컬 금융 조회는 고정 fixture이고 입출금 호출은 실패하도록 격리한다. 청구·알림 정기 작업과 결제 복구 작업은 test 설정에서 꺼져 있다. 금융망 연동·새 계좌 연결·실제 잔액 변화·정기 처리 타이밍은 이 앱으로 검증할 수 없다. 이를 숨기기 위해 성공 응답이나 지급 완료 데이터를 추가하지 않는다.

현재 시드의 급여·월세·정기 구독·예정 이체·금액 미정 일정은 가계부에 저장한 예시 입력이지 운영 기본 제공 항목이 아니다. 카드 실적은 과거 구매의 집계이고, 상품 한도는 카탈로그 정책이다. 상품 정책의 과거 투영 한계는 LIFE-BENEFITS.md에 명시한다.

이번 점검에서 5개 화면의 실제 UI 텍스트를 `build/local-app/parity-*.xml`에 남겼다(로컬 검증 산출물, 커밋 제외). 화면 조회 외 데이터 변경·재시드·카드 해제·실제 금융거래·RDS 적재는 하지 않았다.

검사 보강:
- `check-local-bindings.ps1`: debug/release 실제 Repository 연결과 로컬 대체 서비스 범위를 확인한다. 배포 버전이나 시드 최신성까지 보장하지 않는다.
- `check-local-app.ps1`: 표시문구 검사 정규식의 공백·단어 경계를 수정하고 QA/p숫자/테스트/더미를 검사한다. 이 HTTP 검사는 기기를 재등록하므로 기존 에뮬레이터 세션을 끊을 수 있어 이번 점검에서는 재실행하지 않았다.
- 스크립트 바인딩 검사와 표시문구 양성/음성 검사를 통과했다.

### 2026-11-16 최신 혜택 시드 로컬 반영 완료

위 점검에서 발견한 **최신 혜택 시드 미적용**은 사용자 승인 후 해소했다. AI 미연결, 금융 어댑터 격리, 실행 중인 서버/앱 기반 커밋 차이는 이번 혜택 이관의 대상이 아니다.

- `QaLifeBenefits.apply`를 신규 시드 생성과 기존 로컬 이관이 공유한다. 정책 계산 결과 JSON과 기존 엔진은 바꾸지 않았다.
- 기존 395개 구매의 ID·원금·상태를 보존하고 가입 후 234개를 최신 LIFE의 YAMU 이력으로 연결했다. 가입 전 161개는 SEED 유지.
