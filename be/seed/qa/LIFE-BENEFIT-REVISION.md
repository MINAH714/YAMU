# LIFE 과거 혜택 확정 및 11월 즉시 할인 반영

## 변경 내용

세 사용자 모두 동일하게 적용한다. 실제 지급·금융망 입출금은 실행하지 않는다.

- 2026년 4~10월 혜택에 `confirmed_at=2026-11-15 15:00:00 UTC`(11/16 00:00 KST), `confirmation_source=QA_HISTORY`를 기록한다. 이는 기준일 현재 확정 완료로 구성한 QA 시나리오이지 실제 지급일·외부 지급 증빙이 아니다. 원금·혜택액·포인트 환산율은 변경하지 않는다.
- 기존 11/8 IBK 22,000원 식당 구매 1건을 GS25 제육도시락 5,500원 × 4개로 변경한다. 구매 ID·요청 원금·일자·실적 인정액은 유지한다. 현장할인 2,200원, 승인액 19,800원, 하루 할인 횟수 1회 사용을 저장한다.
- 즉시 할인은 현재 `GS25_INSTANT_10` 정책과 검증된 POS 상품 구성을 기존 계산기로 계산했다. 계산 범위는 이 현장할인 서비스 하나이며 중복 캐시백 등 미확인 혜택은 추가하지 않는다. basket과 calculationScope를 원거래 스냅샷에 남긴다.
- 구매는 사용자별 395건 유지. 11월 소비 원금은 690,000원 유지, 11월 혜택은 총 3,200원(확정 2,200원 / 예정 포인트 1,000원).
- 4~10월은 월별 확정 전 0원, 확정액은 기존 총 혜택과 같다. 11월 청구 896,500원 / 12월 초기 누적 420,000원은 변경하지 않는다.
- IBK 합성 과거 원장이 이미 설치되어 있으면 11/8 체크 출금도 19,800원으로 다시 구성한다. 종료 잔액 300,000원을 유지하도록 과거 시작 조건을 135,000원에서 132,800원으로 역산한다. 보정 입출금은 만들지 않는다. 국민·신한 원장과 SSAFY 원본은 변경하지 않는다.
- 일반 사용자 결제는 기존 확정 판정을 유지한다. QA 확정 근거는 qa_seed_member에 등록된 사용자의 QA_LIFE_550 원거래에만 적용한다.
- 신규 시드의 예정 수입 명칭은 `월급`이다(250만 원, 매월 26일). 현재 로컬 앱의 기존 일정·발생 건도 이름만 변경했다.

## 신규 적재

최신 마이그레이션과 시드로 기존 apply → 계정 준비 → enrich → verify 절차를 사용한다. 혜택 확정과 즉시 할인은 apply에 포함된다. 이 변경이 계정 준비나 로그인 도구를 제공하지는 않는다.

## 이미 적재된 세 사용자 반영 절차

담당자가 승인된 운영 변경 창에서 실행한다. 작성자는 운영 DB에 실행하지 않았다.

1. 이 변경이 포함된 BE와 `V20261116_5__add_benefit_confirmation_evidence.sql`을 함께 반영한다. 새 조회 SQL은 새 컬럼이 필요하다. 기존 운영 버전만으로 시드 데이터만 수정해서는 과거 포인트가 확정 표시되지 않는다. Flyway 이력·카탈로그·LIFE/IBK 호환성을 확인한다.
2. 세 데이터셋 `qa-550-life-1~3`의 실제 사용자 매핑을 확인한다. 보고된 사용자 11·12·13과 다르면 멈추고 확인한다. 대상 사용자의 DB 백업과 현재 입력 파일·설정으로 복구 가능한지 확인한다. 사용자 변경/결제 작업과 관련 배치를 멈추되 금융 출금 배치를 새로 켜지 않는다.
3. 기존 apply에 사용한 사용자별 입력과 금융 바인딩 및 동일 암호화/HMAC 설정을 사용한다. 공개 example만으로 실행하지 않는다. 계좌/PIN/기기는 수정하지 않는다. 유지보수 환경변수 `QA_SEED_MAINTENANCE=true`를 지정한다.
4. 각 데이터셋의 `HEX(input_hash)`를 읽어 검토한 값을 `QA_SEED_EXPECTED_INPUT_HASH`에 설정한다. 비밀키가 아닌 입력 지문이다. 명령은 데이터셋 잠금 안에서 이 값이 아직 일치하는지 재검사한다. 불일치 오류를 우회하거나 DB 지문을 수동 덮어쓰지 않는다.
5. BE 폴더에서 사용자별로 아래 명령을 실행한다. `<기존 사용자 입력 파일>`은 각 사용자의 실제 승인된 입력 파일로 바꾼다.

```powershell
.\gradlew.bat -I seed/qa/qa.init.gradle classes seedQa -PqaCommand=revise-benefits -PqaFile=<기존 사용자 입력 파일>
.\gradlew.bat -I seed/qa/qa.init.gradle seedQa -PqaCommand=verify -PqaFile=<기존 사용자 입력 파일>
```

6. 명령은 각 데이터셋 단위 트랜잭션이다. 기존 395개 구매의 소유권·결정적 요청키·카드/계좌 바인딩·원금·시각·상태를 검사한다. 변경된 구매나 이미 별도 혜택이 붙은 대상은 덮어쓰지 않고 실패/롤백한다. 후속 QA 구매는 유지한다. 성공하면 새 입력 지문을 저장하므로 이후 일반 enrich/verify가 최신 시드와 일치한다.
7. PENDING 계정이어도 이 보정은 가능하다. 청구서·알림이 아직 없는 계정은 기존 가입 준비 완료 후 enrich를 실행한다. 이미 enrich된 계정은 기존 청구서·알림 ID·읽음 상태를 보존하며 해당 즉시 할인 결제 알림만 갱신한다. 계정 준비 절차와 이번 데이터 보정은 별개다.
8. 세 사용자 각각 4~10월 혜택 API에서 `unconfirmedBenefit=0`, `confirmedBenefit=expectedBenefit`을 확인한다. 11월은 확정 2,200 / 예정 1,000원, 할인 거래 승인액 19,800원, 청구액과 기존 구매 건수, 계정 간 데이터 분리를 확인한다. 새 지문을 다시 확인한 재실행에서 혜택·한도 행이 늘어나지 않아야 한다.

## 실패와 복구

- 입력 검사·중간 SQL·과거 잔고 검증 실패 시 해당 데이터셋 변경 전체를 롤백한다. 세 데이터셋 전체가 하나의 트랜잭션은 아니므로 사용자별 결과를 기록한다.
- 이미 성공한 변경을 되돌릴 때는 대상 행 백업과 입력 지문, 합성 원장을 함께 복구한다. 이후 사용자 활동이 있으면 일괄 복구하지 않는다. reset/purge로 가입·구매 이력을 지우지 않는다.
- 금융망 입출금, 시작 자금 입금, 출금 배치 실행은 절차에 없다. RDS 반영은 담당자가 위 절차로 별도 수행한다.

### 후속 로컬 앱 적용

2026-11-16 사용자 요청으로 실행 중인 로컬 앱 DB에도 적용했다. 기존 계정·PIN·기기·구매 ID를 유지하고 `revise-benefits`와 `verify`를 실행했다. 운영/RDS는 적용하지 않았다.

- 에뮬레이터 연결: `tcp:18550` → 최신 로컬 서버 `127.0.0.1:18559`. 현재 앱 DB는 격리 컨테이너 `aef5c46106fa`의 `test_1`이며, 이전 로컬 DB `86638c789867/test_1`에도 동일 개정이 적용되었다.
- 백업: 무시되는 `be/build/local-resume/before-current-app.sql`(현재 앱), `before.sql`(이전 로컬 DB). 인증·암호화 데이터가 포함되므로 공유·커밋하지 않는다.
- `resumeLocalApp` 태스크는 loopback 테스트 DB만 허용하며 DB 생성·삭제 없이 재사용한다. 금융 클라이언트는 mock이고 입출금은 거부한다. 기존 DB 컨테이너를 유지해야 한다.
- 화면에서 8월 3,500원·9월 6,500원·10월 3,500원 모두 확정, 11월 확정 할인 2,200원/확정 전 적립 1,000원을 확인했다. 11월 혜택 리포트를 열어 두었다.
- 이 로컬 실행은 develop 통합 전 마이그레이션 번호를 사용했다. 최신 develop의 기존 V20261116_4와 충돌하지 않도록 배포 파일은 V20261116_5로 정리했다. 이 임시 로컬 DB를 최신 소스로 다시 시작할 때 Flyway repair를 임의 실행하지 말고, 백업을 보존한 상태에서 새 격리 미리보기를 사용한다. 현재 실행 중인 서버는 유지된다.
